# 用户邮箱绑定功能优化计划

## 一、现状梳理

项目共有三处实现了「邮箱绑定 / 解绑 / 换绑」三种操作，覆盖三端：

| 端 | 文件 | 入口 UI | 调用层 |
| --- | --- | --- | --- |
| Admin | `apps/admin/src/pages/account/settings.tsx:48-441,612-764` | 页面内 Tag + 三个按钮 | `adminApi.bindEmail / unbindEmail / changeEmail` (走 `/api/v1/admin/me/email/*`) |
| Doctor | `apps/doctor/src/app.tsx:109-298,442-591` | 顶部下拉菜单 → `Modal.confirm` 二次确认 | `doctorApi.emailBind / emailUnbind / emailChange`，内部转发到 `accountApi.*` (走 `/api/v1/accounts/me/email/*`) |
| Patient (H5) | `apps/patient-h5/src/pages/profile/edit.tsx:20-505` | 表单项点击 → `Dialog.show` 二次确认 | **`authApi.emailBind / emailUnbind / emailChange / sendEmailCode`（已 deprecated 的旧接口 `/api/v1/auth/email/*`）** |

后端实现：
- 推荐统一接口：`apps/server/app/modules/accounts/router.py:269-378`（按 `account_bind` 场景生成/校验验证码）。
- 兼容旧接口：`apps/server/app/modules/auth/router.py:705-928`（已标记 `deprecated=True`，按 `bind` 场景生成/校验）。
- Admin 旧接口：`apps/server/app/modules/admin/router_auth_password.py:85-` 仍在使用，并未迁到 accounts。

API SDK 层：
- `packages/api/src/modules/account.ts`：统一账号接口（推荐，`code_type: 'bind'` 但场景在后端为 `account_bind`）。
- `packages/api/src/modules/admin.ts:354-394`：admin 单独的 `/admin/me/email/*` 接口。
- `packages/api/src/modules/doctor.ts:256-289`：doctor 接口已转发到 accountApi，无独立实现。
- `packages/api/src/modules/auth.ts:249-311`：旧的 `/auth/email/*` 接口（被 patient-h5 使用）。

## 二、发现的问题

### 2.1 逻辑/Bug 类（高优）

1. **patient-h5 仍使用 deprecated 接口**（`apps/patient-h5/src/pages/profile/edit.tsx:131,152,185,192,199`）
   - 后端 `/auth/email/bind|unbind|change` 已标 `deprecated=True`，验证码 scenario 为 `'bind'`；而新统一接口使用 `'account_bind'`。
   - 这导致 patient-h5 与 admin/doctor 行为不一致，未来后端清理 deprecated 路由时会直接故障。

2. **patient-h5 解绑时 send-code scenario 错误**（`apps/patient-h5/src/pages/profile/edit.tsx:152`）
   - 解绑时 `await authApi.sendEmailCode(user.email, 'bind');` —— 后端 `auth/email/unbind` 校验时用 `verify_email_code(user.email, code, "bind")`（`apps/server/app/modules/auth/router.py:906`），目前是匹配的。但语义上「解绑」用 `bind` scenario 容易混淆，迁到 accounts 接口后这个问题自动消失。

3. **admin 端旧 send-code 接口仍在用**（`packages/api/src/modules/admin.ts:355,368`）
   - `sendEmailCode` 走 `/admin/email/send-code`（用于登录），`sendProfileEmailCode` 走 `/admin/me/email/send-code`（用于绑定）；正常使用没问题，但 admin 的绑定/解绑/换绑都走 `/admin/me/email/*` 而非统一的 `/accounts/me/email/*`，与 doctor 端不一致。

4. **倒计时定时器未在解绑/换绑场景独立隔离**（admin/doctor）
   - 解绑场景下，「获取验证码」按钮调用的是 `handleSendEmailCode('new')`（`apps/admin/src/pages/account/settings.tsx:684`），但 `'new'` 分支会读 `emailForm.getFieldValue('email')`，这在解绑表单里没有 email 字段，导致点击后弹出 `请先输入邮箱` 错误。
   - **复现**：admin 端「解绑邮箱」弹窗 → 点击「获取验证码」→ 报错 `请先输入邮箱`。
   - 应为：解绑场景应调用 `handleSendEmailCode('old')`（向当前已绑定邮箱发送）。
   - doctor 端 `apps/doctor/src/app.tsx:512` 同样 bug。

5. **换绑时换绑成功后未同步刷新全局 user 状态（patient-h5）**（`apps/patient-h5/src/pages/profile/edit.tsx:209`）
   - 仅调用 `loadProfile()` 刷新本地 state，全局可能用 `useModel('@@initialState')` 的位置不会同步。需要核对 patient-h5 是否使用 initialState。

6. **倒计时与组件卸载竞态**：`emailTimerRef` 仅在 useEffect cleanup 时清理，关弹窗时 `setEmailModalVisible(false)` 不清 timer，下次重新打开可能继承旧倒计时（`apps/admin/src/pages/account/settings.tsx:616, apps/doctor/src/app.tsx:446`）。

7. **同一邮箱重复绑定校验前置不足**：前端没做「新邮箱 == 当前邮箱」的提示，等到提交才会被后端 `_is_email_taken_in_tenant` 拒绝，体验不佳。

8. **错误信息一致性**：emailBind 失败时（如「该邮箱已被其他账号绑定」）后端返回中文信息，但 admin 端 `handleEmailSubmit` catch 中 `if (error.message)` 才弹（`apps/admin/src/pages/account/settings.tsx:319-322`）；patient-h5 用 `error.message || '操作失败'` 兜底（`apps/patient-h5/src/pages/profile/edit.tsx:211`）；不一致。

### 2.2 UX/UI 类（中优）

1. **admin 端入口分散**：邮箱在「基本信息」表单里以 Tag + 多个独立按钮的形式展示，与「姓名/手机号」字段视觉割裂。建议统一为「带操作图标的输入展示行」（类似 doctor/h5 的列表项样式）。

2. **doctor 端入口隐藏过深**：必须从右上角下拉菜单点开「邮箱管理」→ 再用 `Modal.confirm` 二次确认（更换/解绑），交互层级过多；且 `Modal.confirm` 用 OK/Cancel 表达「换绑/解绑」语义不直观，用户容易误点（cancel 居然代表「解绑」）。建议改为底部弹层或独立的「我的资料」页统一管理。

3. **patient-h5 弹窗按钮文案**：`closeOnAction` 与 `e?.preventDefault?.()` 同时存在，逻辑混乱；表单校验不通过时弹窗会被关闭（应阻止）。

4. **验证码倒计时按钮文案**：admin/doctor 写为 `${countdown}s`，patient-h5 也是 `${countdown}s`，但都没显示「重新发送」语义。建议改成 `重新发送(60s)` 这种更清晰的格式。

5. **缺少邮箱掩码展示**：解绑/换绑时弹窗显示完整邮箱（如 `xxx@example.com`），可考虑遮罩中段（`x***@example.com`），尤其在公共场景。

6. **缺少加载/骨架状态**：admin 邮箱区块在 `loadAdmin` 期间无骨架，`admin?.email` 为 undefined 时短暂显示「未绑定」按钮，再切换为「已绑定」状态，存在闪烁。

7. **绑定/换绑成功后无明显视觉强化**：仅 `message.success`，建议在邮箱行加入「✓ 已绑定 yyyy-MM-dd 绑定」的辅助信息。

8. **可访问性**：所有「获取验证码」按钮缺少 `aria-label`（倒计时状态对屏幕阅读器不友好）；邮箱输入未指定 `autoComplete="email"`、`inputMode="email"`。

9. **邮箱大小写**：前端 input 大小写按用户输入保留，后端在 `_normalize_email` 转小写。前端可在 onBlur 时自动小写，避免用户视觉困惑。

10. **换绑表单中两个「获取验证码」按钮**：旧邮箱和新邮箱都有验证码按钮，倒计时各自独立；但 UI 上两个按钮挨得近，缺少视觉区分（如分组标题「身份验证 / 新邮箱验证」）。

### 2.3 代码层面（低优，但与本次抽取相关）

1. **三端表单 + 倒计时 + 提交逻辑高度重复**（admin / doctor / patient-h5 各 200~250 行），存在三份几乎相同的 `handleSendEmailCode / handleEmailSubmit / openEmailModal`。
2. **doctor 端把整个邮箱模态塞进 `app.tsx` 的 `layout` runtime config**，导致 `app.tsx` 文件臃肿（649 行）且不便测试。
3. **timer 引用 + 倒计时 state 散落**，没有用 `useCountdown` 之类的小 hook 封装。

## 三、优化方案

### 3.1 共享层：抽取 `useEmailBinding` hook 与 `EmailBindingForm` 组件

**位置**：在 `packages/api`（或新建 `packages/hooks`，按当前 monorepo 习惯先放在 `packages/api/src/hooks/`）。

新增：
- `packages/api/src/hooks/useCountdown.ts`：通用倒计时 hook，封装 `start(seconds)` / `reset()` / `count` / `running`，自动处理 unmount cleanup。
- `packages/api/src/hooks/useEmailBinding.ts`：核心业务 hook
  - 输入：`{ currentEmail, onSuccess, api?: { sendCode, bind, unbind, change } }`（默认使用 `accountApi`）。
  - 状态：`mode: 'bind' | 'unbind' | 'change'`、`open`、`submitting`、`newCodeCountdown`、`oldCodeCountdown`。
  - 方法：`openModal(mode)`、`closeModal()`、`sendNewCode(email)`、`sendOldCode()`、`submitBind(values)`、`submitUnbind(code)`、`submitChange(values)`。
  - 内部统一处理：邮箱格式校验、相同邮箱前置检查、错误 message 透传、timer cleanup。

可选共享 UI：
- 因 admin（PC，antd）、doctor（PC，antd）、patient-h5（H5，antd-mobile）UI 库不同，**不建议**抽取统一 UI 组件。但可以分别抽到：
  - `apps/admin/src/components/EmailBindingModal.tsx`（admin/doctor 共用 antd，可放 `packages/ui-pc` 或者各自维护一份精简后的组件）。
  - `apps/patient-h5/src/components/EmailBindingDialog.tsx`（antd-mobile 专用）。
- 优先方案：**只共享 hook，不共享 UI 组件**——保持各端样式自由，减少无谓抽象。

### 3.2 分端迁移与 UI 优化

#### 3.2.1 patient-h5（最重要，bug 修复）

**文件**：`apps/patient-h5/src/pages/profile/edit.tsx`、`packages/api/src/modules/auth.ts`

修改：
1. 把 `authApi.sendEmailCode/emailBind/emailUnbind/emailChange` 替换为 `accountApi.*` 调用。
2. 引入 `useEmailBinding`，删除本地 200+ 行重复逻辑。
3. UI 改进：
   - 「获取验证码」按钮显示 `重新发送(60s)`。
   - 「确认」按钮校验失败时阻止 Dialog 关闭（修正 `closeOnAction` + `e.preventDefault` 矛盾）。
   - 输入加 `inputMode="email"`、`autoComplete="email"`、自动小写。
   - 解绑时邮箱掩码展示（`x***@example.com`）。
   - 成功后同步全局用户 state（如有）。

#### 3.2.2 admin（修 send-code bug + 入口优化）

**文件**：`apps/admin/src/pages/account/settings.tsx`、`packages/api/src/modules/admin.ts`

修改：
1. **修 bug**：`emailModalType === 'unbind'` 时「获取验证码」按钮的 `onClick` 改为 `handleSendEmailCode('old')`，并使用 `emailOldCodeCountdown` 状态。
2. 接口统一：把 `adminApi.sendProfileEmailCode/bindEmail/unbindEmail/changeEmail` 内部委托到 `accountApi.*`（保留旧导出做兼容）；或直接在页面里换用 `accountApi`。
3. 引入 `useEmailBinding`。
4. UI 重构：邮箱区块改为列表行（label 左对齐 + 右侧 `xxx@example.com 已绑定 [更换] [解绑]`），与「姓名/手机号」视觉一致。
5. 加入加载骨架，避免「未绑定」闪烁。
6. 倒计时按钮文案改 `重新发送(60s)`。
7. 关弹窗时清理 timer。

#### 3.2.3 doctor（修 send-code bug + 入口优化）

**文件**：`apps/doctor/src/app.tsx`、新建 `apps/doctor/src/components/EmailBindingModal.tsx`、新建 `apps/doctor/src/pages/profile/index.tsx`（如不存在）

修改：
1. **修 bug**：unbind 模式获取验证码改为 `handleSendEmailCode('old')`。
2. 把邮箱模态从 `app.tsx` 拆出到 `components/EmailBindingModal.tsx`。
3. 入口调整：
   - 把「邮箱管理」从下拉菜单移到独立的「个人资料」页（如已有则直接挂入），下拉菜单仅保留入口跳转。
   - 已绑定时不再用 `Modal.confirm` 的 OK=换绑、Cancel=解绑（语义错乱）；改为页面内并列两个独立按钮。
4. 引入 `useEmailBinding`。
5. UI 同 admin。

### 3.3 后端（不强制本次落地，记录）

- 后续把 admin 的 `/admin/me/email/*` 全部迁到 `/accounts/me/email/*`，删除 deprecated `/auth/email/*`。本次仅前端切换，后端保留，不破坏兼容。
- patient-h5 切到 accounts 接口后，需要确认 `_is_email_taken_in_tenant` 在患者租户下的实现（`apps/server/app/modules/accounts/router.py:320` 引用），避免新接口下出现「同租户多 user 共享邮箱」回归问题。

## 五、测试计划

1. **手工验证**（三端）：
   - 未绑定 → 绑定（正确邮箱 + 验证码）。
   - 已绑定 → 解绑（向当前邮箱发码 → 校验通过）。
   - 已绑定 → 换绑（新旧邮箱各自发码 → 校验通过）。
   - 错误路径：邮箱格式不正确、验证码错误、邮箱已被占用、60s 内重复发码、新邮箱与旧邮箱相同。
   - 边界：弹窗打开 → 倒计时中 → 取消关闭 → 重新打开倒计时归零。
   - admin 与 doctor 的 unbind 「获取验证码」按钮（修 bug 验证）。
2. **单元/集成**：
   - 给 `useCountdown` 写 vitest 测试（fake timers）。
   - 给 `useEmailBinding` 写测试（mock api，覆盖三种 mode 的成功/失败）。
3. **回归**：
   - patient-h5 老接口可被新接口替代；运行 `apps/server/tests/integration/test_users_and_upload_endpoints.py` 中的 `/api/v1/accounts/me/email/bind` 用例。
   - 检查 `apps/admin-v2`、`apps/patient-miniapp` 是否使用了相关接口（已确认未使用）。

## 六、风险与回滚

- **风险 1**：patient-h5 切到 accounts 接口后，若该端用户在 Account 表的 sync 状态不一致，可能出现「绑定失败 邮箱已被使用」误报。**缓解**：发布前先在 staging 跑一遍患者绑定流程；保留旧 `authApi.email*` 函数不删除，必要时可一行回滚。
- **风险 2**：admin 端把「基本信息」里的邮箱区块改成新布局，可能与现有截图/文档不一致。**缓解**：仅做视觉调整，不改字段含义；同步更新 `reviews/ux-facts-collection.md` 之类的文档。
- **风险 3**：抽取 hook 到 `packages/api` 引入 React 依赖。**缓解**：把 hooks 放在子路径 `packages/api/src/hooks/`，并在 `package.json` 的 `peerDependencies` 中声明 `react`，避免污染纯请求层。
