## Context

当前自动排班定时任务由 Beat 每天凌晨 2:00 触发 `auto_generate_schedules_task`。该任务在一个进程里：
- 查询全部活跃租户
- 逐个切换租户上下文
- 逐租户查询模板并生成排班
- 在同一个顶层任务里统计总结果并处理重试

这种实现的优点是简单，但有两个明显问题：
- 总耗时与租户数线性增长，租户变多后会占用更长的 scheduled worker 窗口
- 顶层任务一旦触发重试，会把所有租户重新纳入处理范围，失败域过大

## Goals / Non-Goals

**Goals:**
- 将自动排班的并行粒度提升到“租户”
- 保留租户内模板级错误隔离和现有排班生成规则
- 为调度结果提供结构化汇总，方便日志、监控和后续告警
- 确保重复触发时不会因并行化引入重复排班

**Non-Goals:**
- 本次不改 Admin 手动生成排班接口
- 本次不把模板内的日期/时段循环再继续拆成更细粒度任务
- 本次不调整排班生成业务规则本身（休息日、重复排班检测、时间槽拆分等）

## Decisions

### 1. 采用三段式任务编排

新增三个任务角色：
- `auto_generate_schedules_task`: 仅负责发现活跃租户并派发任务
- `generate_schedules_for_tenant_task`: 负责单租户内的模板生成
- `summarize_auto_generate_schedules_task`: 汇总租户子任务结果并输出最终统计

Beat 仍然只触发 `auto_generate_schedules_task`。调度器使用 Celery `chord` 或等价的 fan-out/fan-in 方式，把活跃租户拆成多个租户任务；所有租户任务完成后，再由汇总回调统一产出统计结果。

### 2. 复用现有租户内逻辑，不改变模板级事务边界

当前代码里“查询模板 -> 循环日期 -> 跳过已存在排班 -> 提交模板事务”的逻辑已经具备较好的业务正确性。并行化时不重写该部分规则，只把它从顶层串行任务中抽到单租户任务里，确保：
- 每个模板继续使用独立事务
- 单模板失败不影响同租户其他模板
- 单租户失败不影响其他租户

### 3. 顶层任务不阻塞等待子任务逐个完成

调度器只负责派发任务并返回任务编排信息，不在自身内部串行等待每个租户结果。最终汇总由回调任务完成，以减少顶层任务持有 worker 时间、避免再次退化为“串行等待并行任务”。

### 4. 并行后仍以现有唯一性检查保障幂等

现有生成逻辑在写入前会检查相同医生、日期、开始/结束时间的排班是否已存在。并行化不会改变这个检查，也不会把同一个租户拆成多个并发生成任务，因此重复触发时仍应以“已存在则跳过”为主保障，避免重复排班。

### 5. 汇总结果必须携带租户级别细节

汇总回调输出至少包含：
- 派发租户数
- 成功/失败租户数
- 创建/跳过的总排班数
- 每个租户的 created/skipped/template_count/error 摘要

这样既能保持现在的可观测性，也方便后续接监控或告警。

## Risks / Trade-offs

- 并行任务数会随着活跃租户数增长，需要依赖现有 Celery worker 并发控制，不能无限 fan-out
- `chord`/回调要求结果后端稳定可用；如果结果后端不稳定，需要退回到 group + 独立汇总轮询方案
- 汇总日志会比现在更分散，需要统一 task name 和日志字段

## Migration Plan

1. 先抽出单租户生成任务，保证与现有串行实现产生同样的统计结构
2. 再让顶层任务改为 fan-out 调度
3. 最后接入汇总回调与针对性测试

## Open Questions

- 当前 scheduled queue 的 worker 并发上限是否需要单独调优
- 汇总结果是否需要持久化到表，还是先维持日志级可观测性即可
