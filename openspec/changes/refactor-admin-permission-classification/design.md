## Context

当前权限系统已经具备以下基础能力：
- 后端通过 `require_permission(...)` 做接口级权限拦截
- 前端通过 `access.ts` 与 `hasPermission(...)` 做菜单、按钮和页面显隐
- 角色权限以权限码数组形式存储，`SUPER_ADMIN` 拥有全量权限
- Admin 端已有权限树接口和角色分配页

但现有模型存在一个核心断层：**系统知道怎么校验权限，却没有很好地表达权限的“控制对象”**。例如：

- `store` 更像页面入口
- `schedule:template` 更像页内视图或业务子页
- `system:user:reset-password` 明显是按钮操作
- `appointment:detail`、`store:list`、`log:export` 更接近数据接口或数据能力

如果仍只显示 `menu/button`，角色配置者很难快速判断某个权限会对 UI 和数据访问产生什么影响。

## Goals / Non-Goals

**Goals**
- 让角色配置者可以按“控制类型”理解权限，而不是只看代码层树结构
- 降低分配权限时的搜索成本、判断成本和误配风险
- 保持现有权限码、存储结构与后端接口校验不变
- 形成可渐进升级的分类规则，为后续后端元数据补齐预留接口

**Non-Goals**
- 不在首期变更中改写整个权限模型或数据库结构
- 不要求每个权限码都变成严格唯一的单一业务类型
- 不在本次变更中重构所有菜单、路由或页面权限守卫

## Decision

### 1. 采用“双维分类”而不是替换现有 `type`

保留后端现有 `Permission.type = menu | button`，同时在 Admin 端引入新的展示层字段：

- `moduleGroup`: 业务模块分组，如门店、排班、预约、系统设置
- `controlType`: 控制类型，如页面、Tab/视图、按钮/操作、接口/数据能力

这样做的原因：
- 避免首期改数据库与初始化脚本，风险更低
- 可以直接复用现有权限树 API
- 如果后续分类稳定，再下沉为后端正式元数据

### 2. 控制类型采用规则推导，不依赖人工逐条维护

首期分类由权限码、树层级和命名语义综合推导：

#### 页面
- 顶层模块权限，如 `store`、`doctor`、`appointment`
- 明确表示页面访问的权限，如 `dashboard`

#### Tab/视图
- 控制某个模块下的子页、视图切换或业务工作台
- 例如：`schedule:template`、`schedule:custom`、`schedule:rest-day`、`schedule:suspension`、`schedule:statistics`
- 例如：`content:news`、`content:notice`、`content:banner`
- 例如：`system:role`、`system:user`、`system:settings`

#### 按钮/操作
- 明确的创建、编辑、删除、审批、退款、发送、重置密码等行为权限
- 常见后缀：`create`、`update`、`delete`、`approve`、`refund`、`send`、`reply`、`reset-password`、`manage`、`cancel`

#### 接口/数据能力
- 偏向查看、列表、详情、导出、统计等数据访问能力
- 常见后缀：`list`、`detail`、`view`、`export`、`statistics`

说明：
- 某些权限天然具备双重语义，但首期展示采用“主类型”即可
- 如有需要，可在 UI 中补充次级标签，如“接口联动”“数据查看”

### 3. 分配页从“单树勾选”重构为“概览 + 筛选 + 分组编辑”

建议结构：

```text
页头：角色信息 + 权限总览
筛选区：关键词、类型筛选、仅看已选、展开/收起、批量操作
主体区：
  左侧/上方：模块列表与模块统计
  右侧/下方：按模块展开的权限组，每组内部按控制类型分段
底部：已选摘要 + 保存
```

交互原则：
- 先看到模块和类型分布，再进入逐项勾选
- 批量操作优先对“模块”和“类型”生效，而不是只对整棵树生效
- 保存前给出当前角色的权限概况，降低误保存风险

### 4. 保存协议保持不变

尽管展示结构变化较大，最终提交给后端的仍然是 `string[]` 权限码数组：

- 不修改 `PUT /admin/roles/{id}/permissions`
- 不修改 `Role.permissions` 的存储方式
- 不要求后端理解前端的展示分类

这能保证首期改造只发生在 Admin 端体验层，不影响线上鉴权链路。

## UI Behavior

### 总览区
- 显示已选权限总数
- 显示已覆盖模块数
- 显示页面 / Tab / 按钮 / 接口四类权限数量
- 对“高风险操作型权限”给出醒目标识

### 筛选区
- 支持权限名、权限码模糊搜索
- 支持按控制类型多选筛选
- 支持“仅查看已选权限”
- 支持“展开全部 / 收起全部”

### 模块区
- 每个模块显示权限总数、已选数、类型分布
- 每个模块支持一键全选 / 清空
- 模块折叠状态独立维护

### 权限项
- 每个权限项展示：中文名称、权限码、控制类型标签、必要说明
- 对按钮型和接口型权限采用不同视觉语言，避免全都长得一样
- 选中后应在摘要区即时反馈

### 保存反馈
- 保存前显示本次已选概况
- 保存成功后回到角色列表或保留当前页并提示成功，二者需择一
- 若保存失败，保留当前勾选状态，避免用户重新选择

## Risks

### 风险 1：规则推导可能有误分类
缓解：
- 分类规则集中在一个工具文件中，便于持续调整
- UI 展示使用“展示分类”文案，避免误导为后端强制元数据
- 对已知特殊权限提供显式覆盖映射

### 风险 2：页面重构后批量选择与树勾选状态不一致
缓解：
- 统一维护单一 `checkedKeys` 数据源
- 所有模块操作、类型操作和搜索视图都基于同一权限集合做增删

### 风险 3：权限数量继续增长时 UI 再次失控
缓解：
- 采用模块 + 类型双重分组
- 为后续后端正式分类字段升级预留空间

## Implementation Notes

首期优先新增前端工具层：
- `normalizePermissionTree(...)`
- `inferPermissionControlType(...)`
- `groupPermissionsByModule(...)`
- `summarizeSelectedPermissions(...)`

这能让角色分配页具备稳定的数据转换层，避免把规则直接散落在 JSX 中。
