# Change: 重构 Admin 菜单信息架构与 SaaS 导航边界

## Why
当前 Admin 端菜单仍带有单院系统的历史结构，平台级 SaaS 能力、租户后台能力、门店业务能力和系统配置能力混在同一导航层级中。与此同时，一部分高频运营配置被隐藏在 `system/settings` 的大 Tab 页或头部快捷入口中，导致功能可发现性、权限边界和长期扩展性都在下降。

## What Changes
- 为 Admin 端建立面向 SaaS 的菜单信息架构，明确平台、组织管理、医疗业务、配置中心、内容运营、系统监控等 6 个导航域
- **菜单命名调整**：组织与权限→组织管理、经营配置→配置中心、内容与触达→内容运营
- **系统监控独立为一级菜单**：将操作日志、签到审计、在线用户、行为分析从"组织与权限"中拆出，独立为"系统监控"导航域
- **settings 全部拆分**：将 system/settings 中的全部 8 个 tab（预约规则、黑名单、微信配置、预约选项、就诊卡配置、医院信息、邮件配置、图片配置）提升为独立菜单入口
- 明确不同角色的菜单可见性边界，特别是平台管理员与租户/门店管理员的导航隔离
- 规定头部快捷入口只能作为加速入口，不能成为唯一入口
- 为已经存在后台 API/页面能力但缺少清晰入口的模块补充导航方案，优先覆盖病历管理与租户订阅/用量
- 对旧版菜单遗留能力建立去向清单，明确"恢复、迁移、合并、废弃"的处理结论

## 已确认决策

1. **"系统监控"作为独立一级菜单** - 从"组织与权限"中拆出，包含操作日志、签到审计、在线用户、行为分析
2. **settings 中的 8 个 tab 全部拆分** - 每个配置项独立为配置中心下的菜单入口
3. **菜单命名调整** - 组织与权限→组织管理、经营配置→配置中心、内容与触达→内容运营
4. **需要先和团队对齐** - 在正式实施前需团队确认菜单命名、settings 拆分优先级、兼容性处理策略

## 待解决问题

- `新闻分类`、`弹框管理` 等旧菜单能力是要恢复实现，还是正式从产品范围中移除
- settings 全部拆分后的优先级和实施顺序（需团队对齐）
- 是否保留原 settings 页面作为过渡期兼容入口（需团队确认）
- 系统监控独立域的权限模型细节（需与安全团队对齐）
