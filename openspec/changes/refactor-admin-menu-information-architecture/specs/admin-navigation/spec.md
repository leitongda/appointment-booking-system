## ADDED Requirements

### Requirement: Admin 端导航必须按 SaaS 管理边界分域组织
系统 SHALL 将 Admin 端导航组织为清晰的管理域，以区分平台管理、组织管理、医疗业务、配置中心、内容运营和系统监控等不同职责边界。

#### Scenario: 平台管理员访问后台
- **WHEN** 平台管理员登录 Admin 端
- **THEN** 系统应展示 6 个导航域：平台管理、组织管理、医疗业务、配置中心、内容运营、系统监控
- **AND** 平台管理应与租户日常业务导航分离，而不是与普通业务菜单并列混放

#### Scenario: 租户管理员访问后台
- **WHEN** 租户管理员或门店管理员登录 Admin 端
- **THEN** 系统不应展示平台级租户管理导航
- **AND** 应仅展示其角色有权访问的组织、业务、配置、内容和监控导航

#### Scenario: 系统监控作为独立导航域
- **WHEN** 用户具备系统审计或监控权限
- **THEN** 系统应展示独立的"系统监控"导航域
- **AND** 系统监控域应包含操作日志、签到审计、在线用户、行为分析等功能
- **AND** 系统监控域应与组织管理域明确分离，职责边界清晰

### Requirement: 配置中心必须提供细粒度的权限控制
系统 SHALL 为配置中心内的各个配置模块提供独立的权限控制点，以支持不同角色管理不同类型的配置。

#### Scenario: 访问配置中心
- **WHEN** 用户具备配置中心访问权限
- **THEN** 系统应仅展示该用户有权管理的配置模块
- **AND** 配置模块应包括：预约规则、黑名单管理、微信配置、预约选项、就诊卡配置、医院信息、邮件配置、图片配置、班次类型、规则组管理、诊费类型、诊费模板、预约须知

#### Scenario: 细粒度配置权限
- **WHEN** 用户仅具备特定配置权限（如仅预约规则配置权限）
- **THEN** 系统应在配置中心域中仅显示预约规则菜单项
- **AND** 不应显示其他无权限的配置模块

#### Scenario: 从 settings 迁移的配置模块
- **WHEN** 用户访问原 system/settings 路径
- **THEN** 系统应自动重定向到新的配置中心对应模块
- **AND** 或显示 deprecation warning 并提供到新菜单的跳转链接

### Requirement: 菜单可见性必须与路由访问权限保持一致
系统 SHALL 通过路由级和菜单级的一致权限模型控制导航可见性，避免仅凭粗粒度父级权限暴露无效菜单。

#### Scenario: 用户仅拥有系统分析权限
- **WHEN** 用户仅具备某个系统子能力权限而不具备完整系统管理权限
- **THEN** 系统应只展示该用户可访问的菜单项或其有效父级容器
- **AND** 不应展示用户无法进入的大量无关子菜单

#### Scenario: 父级菜单没有可访问的有效子项
- **WHEN** 某个父级导航下不存在用户可访问的页面
- **THEN** 系统不应仅为了结构完整而展示空父级菜单

### Requirement: 高频运营配置必须有正式导航入口
系统 SHALL 为高频且职责清晰的运营配置能力提供正式导航入口，而不是仅隐藏在聚合配置页的 Tab 或头部快捷入口中。

#### Scenario: 管理预约规则
- **WHEN** 运营人员需要调整预约规则、黑名单规则或微信配置
- **THEN** 系统应提供可发现的正式入口
- **AND** 这些能力不应只存在于单一的聚合 Tab 页面中

#### Scenario: 使用头部快捷入口
- **WHEN** 用户通过头部快捷入口访问签到二维码、诊费设置或复诊规则
- **THEN** 系统仍应为对应能力提供正式菜单或显式二级导航入口
- **AND** 快捷入口只能作为加速方式，不能成为唯一入口

### Requirement: 已具备后台能力的关键模块必须有清晰导航承接
系统 SHALL 为已存在且面向后台操作的关键能力提供正式菜单入口或清晰的次级导航承接。

#### Scenario: 管理病历
- **WHEN** 后台已支持病历管理能力
- **THEN** Admin 导航中应提供病历管理的正式承接入口

#### Scenario: 查看租户订阅和用量
- **WHEN** 平台管理员需要查看或管理租户订阅与用量
- **THEN** 系统应在租户管理上下文中提供显式入口
- **AND** 这些能力不应只停留在 API 或隐式页面状态

### Requirement: 历史菜单能力的去向必须明确记录
系统 SHALL 对旧版菜单中的历史能力给出去向结论，避免遗留文档与现有产品行为长期不一致。

#### Scenario: 评估旧版菜单项
- **WHEN** 团队盘点旧版菜单中的首页菜单、底部菜单、新闻分类或弹框管理等能力
- **THEN** 每项能力都应被标记为恢复、迁移、合并或废弃之一
- **AND** 不应在没有结论的情况下长期保留模糊状态
