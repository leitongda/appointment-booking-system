# 多风格小程序生成平台设计文档

**Goal:** 在保持现有医疗预约业务逻辑不变的前提下，支持生成多套风格显著不同、信息架构明显不同的小程序应用。

**Architecture:** 第一阶段采用“5 套预制模板 + 实例生成”的方式，先形成可交付的成品模板；第二阶段在稳定模板体系后，升级为“模板 + 配置混合”的生成平台，支持首页、导航、卡片、模块顺序的二次编排。底层继续复用现有患者端业务内核与后端接口。

**Tech Stack:** Taro 4.x、React 18、TypeScript、`@hospital/api`、`@hospital/shared`、FastAPI、OpenSpec

---

## 1. 目标定义

本次不是做一个全新的医疗业务系统，而是做一个“多前端壳层的小程序生成体系”。

固定项：
- 后端接口契约固定
- 登录、预约、支付、签到、消息、就诊人等核心业务结果固定
- 订单、支付、签到等状态流转固定

可变化项：
- 页面信息架构
- 首页模块组织
- 导航结构与入口优先级
- 列表卡片和页面头部布局
- 图标、插画、语气、品牌风格、视觉 token

最终目标是：同一套业务内核，生成多个“看起来像完全不同产品”的小程序实例。

## 2. 第一阶段模板策略

第一阶段采用预制模板生成，不直接开放任意配置拼装。

原因：
- 质量更容易控制
- 交付速度更快
- 可以先验证“模板 -> 实例 -> 发布”的完整链路
- 为后续升级到“模板 + 配置混合”保留空间

第一阶段模板池固定为 5 套：

1. `现代综合医疗`
适合综合医院、门诊、连锁医疗机构，强调标准化、可信赖、信息清晰。

2. `高端专科门诊`
适合口腔、医美、私立专科、会员制门诊，强调品牌感、专家服务和预约体验。

3. `亲子儿科`
适合儿童医院、儿科门诊、家庭健康场景，强调亲和感、家庭成员管理和高频导流入口。

4. `女性健康`
适合妇科、产康、女性体检、专科中心，强调安心感、私密感和持续服务。

5. `长辈友好 / 中医康养`
适合中医馆、康养门诊、老年用户场景，强调低认知负担、大按钮、强引导和信任感。

## 3. 系统架构

平台建议拆成 4 层。

### 3.1 业务内核层

负责稳定承载：
- 登录与会话
- 门店/租户上下文
- 预约挂号
- 支付
- 签到
- 消息
- 就诊人
- 设置与个人中心

这一层优先复用 `apps/patient-miniapp` 现有成熟链路，不直接承载模板差异。

### 3.2 页面壳层层

负责不同模板的页面组织方式，包括：
- 首页模块编排
- 底部导航结构
- 页面头部与内容区布局
- 列表与卡片表现形式
- 页面之间的入口关系

这一层决定“用户看到的小程序长什么样、怎么逛”，但不改变底层业务结果。

### 3.3 模板定义层

负责描述每个模板的静态定义，包括：
- 模板标识与元数据
- 适用行业/人群
- 导航结构
- 首页模块树
- 页面布局规则
- 视觉 token
- 默认插画/图标/品牌资源
- 文案语气规则

第一阶段这里采用“预制模板定义文件”，不开放完全自由编辑。

### 3.4 实例生成层

负责将模板和真实业务实例绑定，生成一个可发布的小程序应用。

实例需绑定：
- 模板
- AppID
- 默认门店
- 租户
- 支付配置
- 品牌名称与 Logo
- 协议/客服/医院介绍等运营内容

## 4. 模板差异边界

为了保证“风格明显不同”同时“不破坏业务”，建议明确差异边界。

### 4.1 允许强差异化的部分

- 首页模块种类与顺序
- tabBar 数量、名称、优先级
- 搜索入口位置
- 预约入口形式
- 医生卡片/科室卡片样式
- 个人中心编排方式
- 页面语气和图形风格

### 4.2 需要保持一致的部分

- 登录认证过程
- 预约创建与重复预约校验
- 支付结果处理
- 签到识别与签到结果
- 消息读写逻辑
- 核心数据模型字段

### 4.3 建议抽象成“可替换壳层”的页面

- 首页
- 科室页
- 医生列表页
- 医生详情页的展示区
- 预约列表页
- 个人中心首页

### 4.4 建议先固定的页面

- 预约确认页
- 支付结果页
- 签到选择页
- 设置页中的功能逻辑

这些页面和交易状态耦合更强，第一阶段不宜做过度自由化。

## 5. 5 套模板的产品定义

### 5.1 现代综合医疗

产品定位：
- 通用型医院模板
- 面向大众用户
- 突出专业、清晰、可信赖

页面特征：
- 经典三栏或四栏快捷入口
- 首页强调预约挂号、科室分类、推荐医生、公告
- tabBar 结构偏标准：首页 / 预约 / 我的

### 5.2 高端专科门诊

产品定位：
- 品牌驱动型专科模板
- 突出医生、服务和品质感

页面特征：
- 首页弱化复杂科室树，强化专家与服务卖点
- 更适合“预约咨询”“医生介绍”“特色项目”前置
- 页面视觉更克制、精致

### 5.3 亲子儿科

产品定位：
- 家庭场景模板
- 突出就诊人切换和儿童高频服务

页面特征：
- 首页可前置“家庭就诊人”“儿童常见服务”“儿保/复诊”
- 图形表达更活泼
- 关键入口更大、更直接

### 5.4 女性健康

产品定位：
- 连续服务型模板
- 强调安心、细致、陪伴

页面特征：
- 首页可前置检查预约、套餐服务、医生咨询、知识内容
- 个人中心强化记录、提醒、反馈
- 文案与视觉更柔和

### 5.5 长辈友好 / 中医康养

产品定位：
- 低认知负担模板
- 面向中医、康养、长辈用户

页面特征：
- 减少首页信息密度
- 使用大字号、大按钮、强引导入口
- 突出快速挂号、我的预约、扫码签到、联系客服

## 6. 模板定义模型

建议每个模板至少包含以下定义。

```ts
interface MiniappStyleTemplate {
  code: string;
  name: string;
  audience: string[];
  description: string;
  navSchema: NavSchema;
  homeSchema: HomeModuleSchema[];
  pageShells: Record<string, PageShellVariant>;
  designTokens: DesignTokenSet;
  assets: TemplateAssetSet;
  tone: CopyToneConfig;
  constraints: TemplateConstraintConfig;
}
```

关键点：
- `navSchema` 决定底部导航和一级入口关系
- `homeSchema` 决定首页模块树和默认顺序
- `pageShells` 决定某个业务页面使用哪种外壳布局
- `constraints` 用于约束哪些业务页面不可替换

## 7. 第一阶段生成流程

建议流程如下：

1. 后台创建小程序实例
2. 选择预制模板
3. 绑定 AppID、默认门店、品牌信息、支付配置
4. 系统写入实例配置与模板引用
5. 构建脚本根据模板生成页面壳层配置
6. 业务内核注入实例信息与门店信息
7. 产出可上传发布的小程序包

第一阶段生成结果应是“完整实例”，而不是“半成品模板项目”。

## 8. 第二阶段升级方向

在预制模板稳定后，再升级到“模板 + 配置混合”。

第二阶段建议开放：
- 首页模块排序
- tabBar 名称与顺序
- 卡片样式切换
- 某些页面壳层切换
- 首页首屏重点模块选择

第二阶段仍不建议完全开放：
- 交易链路页面自由拼装
- 任意接口映射
- 任意状态流转定义

这样可以让平台更强，但不会失控。

## 9. 实施建议

建议按以下顺序推进：

1. 先把模板系统定义出来，而不是先改 UI。
2. 从现有患者端中抽出业务内核和页面壳层边界。
3. 先实现 5 套模板中的 1 套基线模板和 1 套差异模板，验证架构。
4. 再补齐剩余 3 套模板。
5. 最后接入实例生成、构建与发布流程。
