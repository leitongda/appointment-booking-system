## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**产品定义：**
- 营销中台 = 前端营销触点与后端业务系统之间的能力共享层，整合数据/技术/运营能力
- Gartner 对应品类：Multichannel Marketing Hubs (MMH)
- 边界划分：CRM（销售关系）/ CDP（数据统一）/ MA（自动化执行）/ DMP（匿名广告）/ 营销中台（全整合）
- 趋势：边界模糊化，CRM 厂商做 CDP，MA 厂商内置 CDP，DMP 因 Cookie 淘汰衰落
- 部署模式：SaaS（国际主流）/ 私有化（国内金融/政务/医疗）/ 混合云（国内中大型企业主流）

**核心功能模块（9 大模块）：**
1. CDP 能力：多渠道采集、身份合并、统一画像、人群分群、标签体系
2. 营销自动化：旅程编排、触发式营销、A/B 测试、线索评分、频控
3. 内容管理：DAM、模板化、个性化推荐、审批流、多语言
4. 渠道管理：短信/邮件/推送/微信/小程序/社交媒体/广告平台/Web弹窗/线下
5. 活动管理：营销日历、预算追踪、模板复用、ROI 追踪
6. 数据分析与归因：漏斗分析、多触点归因、ROI/ROAS、实时看板、队列分析
7. 人群圈选与标签：可视化圈选、静态/动态人群包、标签层级、Look-alike
8. 权益管理：优惠券/积分/会员等级/核销对账/防刷风控
9. 营销智能：推荐引擎、智能出价、流失/转化/LTV 预测、NLG 文案、发送时间优化

**竞品功能对比：**
- 国内：神策营销云（数据底座强）/ Convertlab（MA 工作流强，国内版 HubSpot）/ 致趣百川（B2B+微信生态）/ 径硕/火眼云（ABM）
- 国际：Salesforce MC（企业级全功能）/ HubSpot（SMB 易用）/ Braze（移动端实时）/ Iterable（跨渠道编排）/ Adobe EC（分析+内容）
- Gartner MMH 2024 Leaders：Adobe、Salesforce、Braze

**目标用户画像：**
- 中小企业（年营收 <1亿）：HubSpot/有赞/微盟，预算 1-10万/年
- 中大型企业（1-50亿）：核心客群，神策/Convertlab/致趣百川，预算 30-150万/年
- 集团（>50亿）：Salesforce/Adobe/自建，预算 100-500万+/年
- 角色：CMO、运营总监、数据分析师、活动运营、内容运营、CRM运营、增长负责人
- 行业：电商零售、金融、教育、医疗、SaaS/B2B、零售快消

**商业模式：**
- 定价维度：按联系人/MAU / 按功能模块 / 按席位 / 按发送量 / 混合
- 实施服务：标准实施 1-3月 / 深度定制 3-12月 / 代运营
- 市场规模：全球 MA 市场 2023 约 55-60亿美元，CAGR 12-15%；全球 CDP 市场 2023 约 50-72亿美元，CAGR 24-34%；中国 MarTech 约 800-1200亿元

### Designer — 用户视角

**用户角色与使用场景：**
- 7 类核心角色：CMO/营销总监（周 2-3次）、运营总监（每日高频）、数据分析师（每日长时间）、活动运营（每日 30-60分钟）、内容运营（每日中频）、渠道运营（每日高频）、系统管理员（周 3-5次）
- 3 条关键旅程：活动策划→执行→复盘；数据采集→洞察→策略调整；触发条件→编排→监控

**信息架构模式：**
- 导航模式：左侧边栏持久导航（HubSpot/ActiveCampaign）/ 顶部+左侧树形（Marketo）/ 顶部水平+上下文侧边栏（SFMC）
- 一级模块划分：按对象（HubSpot）/ 按任务（Mailchimp）/ 按营销链路（国内常见：洞察→策略→创作→投放→评估）
- 数据密集页面布局：仪表盘（KPI监控）/ 列表（管理）/ 看板（审批/状态）/ 日历（排期）/ 画布（旅程编排）

**交互模式：**
- 旅程编排：拖拽画布（主流，Salesforce/Braze/HubSpot 均采用）+ 混合模式（画布+属性面板）
- 人群圈选：条件构建器（主流）/ 可视化标签 / SQL 编辑器 / 混合模式
- A/B 测试：多步骤向导（定义→受众→变体→流量分配→指标→审查）
- 数据可视化：漏斗图、桑基图、管道视图、折线/面积图、热力图、队列分析图

**响应式设计需求：**
- PC 占 65-80%（主工作设备）、手机 15-25%（审批/通知/紧急操作）、平板 5-10%
- 移动端必要模块：审批流程（高）、数据看板概览（高）、紧急操作（高）、消息通知（高）
- 行业主流：独立移动 App 而非纯响应式 Web，移动端为桌面端功能子集

**设计系统与组件库：**
- 组件库：Ant Design（国内企业级市占率最高）/ Arco Design（数据密集型定位）/ Element Plus（Vue 生态最大）
- 自定义组件：旅程画布、漏斗图、人群圈选器、标签管理器、渠道配置器、指标选择器
- 数据表格高级功能：列级筛选、组合筛选保存、批量操作、导出、虚拟滚动、密度切换、列配置

**多租户/多角色 UX：**
- 租户切换：全局导航栏切换器 / 工作区选择器 / URL 路径嵌入
- 权限影响：菜单可见性、操作按钮状态、路由守卫、组件守卫、Feature Flag + RBAC
- 白标范围：Logo/色彩/域名/邮件模板/登录页/字体/CSS注入

### Engineer — 技术视角

**数据存储层：**
- 四类核心数据：用户画像、行为事件、营销活动、触达记录
- 统一 ID 体系：确定性匹配（手机号/邮箱/设备ID）+ 概率性匹配（指纹/行为相似度）
- OLTP：PostgreSQL（RLS/JSONB/丰富索引）或 MySQL（国内部署基数高/ShardingSphere 生态）
- OLAP：ClickHouse（列式/单节点性能）/ Doris（MPP/MySQL 兼容）/ StarRocks（向量化/多表Join）
- 标签存储：宽表（百级标签）/ Bitmap（低基数集合运算）/ 倒排索引 ES（高基数文本）/ 混合方案（行业常见）
- 数据量级：千万级用户、亿级事件/天、标签数据 ~3TB 原始（压缩后 300-600GB）

**核心引擎：**
- 营销自动化：FSM/Statechart 状态机，节点类型（事件/条件/延迟/A-B/动作/结束），实时（秒级）或批量（分钟-小时级）
- 人群圈选：标签集合运算（AND/OR/NOT），实时（Flink 秒级）或离线（Spark 批处理），增量更新机制
- 触达引擎：统一消息模型 + Channel Adapter 模式，频控（Redis 计数器/滑动窗口），指数退避重试
- A/B 测试：确定性哈希（MurmurHash3/xxHash，1000桶），频率学派/贝叶斯，分层正交实验，MAB 算法
- 归因引擎：首次/末次/线性/时间衰减/位置/U-Shaped，数据驱动（Shapley Value/Markov Chain）

**API/协议：**
- 外部集成：广告平台 API（Google/Meta/巨量/腾讯）、短信网关（阿里云/腾讯云/Twilio）、邮件（SendGrid/SES）、微信生态、支付系统
- 数据采集 SDK：Web（DOM事件+Image Beacon/sendBeacon）、移动（自动+手动+本地缓存批量发送）、小程序（生命周期钩子）、服务端
- 实时数据流：Kafka（事件总线）→ Flink（实时标签/人群圈选）→ 存储
- Webhook：HMAC-SHA256 签名、指数退避重试、幂等去重

**安全机制：**
- 多租户隔离：行级（RLS）/ Schema级 / 数据库级 / 混合（中小租户行级+大客户数据库级）
- 内容合规：广告法敏感词（AC自动机/NLP）、反垃圾（SPF/DKIM/DMARC）、审核流程（机器预审+人工复审）
- 隐私保护：GDPR（Opt-in/Right to Erasure）、个人信息保护法、数据脱敏（掩码/哈希/泛化/截断）
- API 安全：OAuth 2.0（Client Credentials/PKCE）、限流（令牌桶/滑动窗口/Redis+Lua）、HMAC-SHA256 签名

**性能与扩展性：**
- 高并发：大促峰值 10-100x、批量触达百万级、人群包 Bitmap 秒级/OLAP 分钟级
- 水平扩展：无状态服务 + 负载均衡、消息队列削峰（Kafka 数十万条/秒）、三级缓存（L1 Caffeine/L2 Redis/L3 DB）
- 一致性：最终一致性（人群包/统计/画像同步）vs 强一致性（优惠券/积分/预算，行锁/Redis原子操作/分布式锁）
- 分布式事务：TCC（跨服务营销执行）/ Saga（长时间旅程）/ 本地消息表（Outbox）

**技术栈选型：**
- 后端：Java Spring Boot/Cloud（国内主流）/ Go（高并发网关）/ Python（数据处理/ML）/ Node.js（BFF/实时推送）
- 前端：React + Ant Design Pro 或 Vue + Element Plus，ECharts/AntV/D3.js
- 大数据：Spark（离线批处理）/ Flink（实时流处理）/ Hadoop/Hive（数据湖）→ 湖仓一体（Iceberg/Delta Lake）
- 消息队列：Kafka（事件总线）/ RabbitMQ（任务队列/延迟消息）/ RocketMQ（电商交易/事务消息）
- 缓存：Redis（丰富数据结构，集群方案 Cluster/Codis）
- 搜索：Elasticsearch（全文检索+聚合）

## Round 3：共识层

### 共识项

1. **议题：9 大模块需 MVP 切分**
   - 结论：9 模块作为全景愿景保留，MVP 聚焦 3 核心模块：CDP（数据+标签+圈选）+ 营销自动化（旅程+触发+频控）+ 渠道管理（短信+邮件+微信+推送）
   - 建议行动：P0 行动项 #1 #2
   - 优先级：P0

2. **议题：GTM 策略和 MVP 定义缺失**
   - 结论：从零规划项目的根本性缺失，必须在技术选型之前完成
   - 建议行动：P0 行动项 #1
   - 优先级：P0

3. **议题：数据量级需分层架构**
   - 结论：SMB（十万级用户）和企业级（千万级用户）需要不同的架构方案
   - 建议行动：P1 行动项 #4
   - 优先级：P1

4. **议题：竞品对比需本地化**
   - 结论：按"国内中大型企业"场景重新梳理，增加渠道生态/部署模式/定价门槛/实施周期维度
   - 建议行动：P1 行动项 #5
   - 优先级：P1

5. **议题：边界定位需明确**
   - 结论：营销中台定位为"集成"而非"替换"，需定义与企业内部系统的集成方案
   - 建议行动：P1 行动项 #7
   - 优先级：P1

### 分歧项

1. **议题：AI 能力的交付时机**
   - 各方立场：
     - PM：NLG 文案可提前到 P0，推荐/预测需数据积累放 P1
     - Designer：AI 辅助交互（自然语言建人群、智能旅程建议）已是竞品标配，应 P0 包含
     - Engineer：AI 需数据基础设施作为前提，建议 P1
   - 裁决：折中方案——P0 包含"AI 原生设计预留"（架构层支持 AI 插件化接入）+ 1-2 个轻量 AI 功能（NLG 文案模板、智能发送时间）；P1 实现完整推荐/预测/智能圈选
   - 决策依据：AI 是竞争力分水岭，但需数据基础。折中方案保证架构前瞻性又不过度承诺

2. **议题：移动端方案（独立 App vs PWA vs H5）**
   - 各方立场：
     - PM：初期 H5 足够，降低成本
     - Designer：PWA 是最佳平衡（离线+推送+无需审核）
     - Engineer：同意 PWA，但 iOS 对 PWA 推送支持有限
   - 裁决：P0 采用响应式 H5 + PWA 增强；有明确客户需求再开发独立 App
   - 决策依据：SaaS 冷启动阶段，覆盖面和迭代速度优先于原生体验

## 被低估的优势

1. **从零规划的技术选型自由度** — 竞品（如 Salesforce MC 通过收购拼合）背负大量技术债务，新项目可直接采用现代架构（事件驱动、微服务、云原生），避免历史包袱
2. **中国市场微信生态深度集成机会** — 国际竞品（Braze/Iterable）对微信支持薄弱，国内竞品虽有支持但通常仅作为渠道之一，这是差异化切入点
3. **LLM 时代后发优势** — 可将 AI 能力原生嵌入产品架构（而非像竞品后期补丁式集成），实现"AI-first"的产品体验

**使用模式：** 对等协作

**关键共识：**

**关键分歧：**
- 2 项需要决策者介入（AI 交付时机、移动端方案）

**Critic 关键洞察：**
- 9 模块定义过于宽泛，需 MVP 切分（否则第一个可用版本交付周期不可控）
- AI 能力不应排到最后，LLM 爆发期竞品已快速迭代
- 缺少 GTM 策略和 MVP 定义是根本性缺失，需在技术选型前完成

**P0 执行状态（2026-05-22）：**
- P0-1 确定行业：**已完成** — 电商零售
- P0-2 确定部署模式：**已完成** — SaaS 优先
- P0-3 评估团队：**已完成** — 5 人以下

### Engineer 补充

**可观测性方案：**
- 日志：结构化日志（JSON 格式）→ ELK（Elasticsearch + Logstash + Kibana）或 Loki + Grafana
- 指标：业务指标（触达成功率、人群包计算延迟、旅程执行吞吐量）+ 基础设施指标（CPU/内存/磁盘/网络）→ Prometheus + Grafana
- 链路追踪：分布式调用链追踪 → Jaeger 或 SkyWalking（Java 生态友好）
- 告警策略：P0（核心链路中断，立即通知）→ P1（性能退化，15分钟内）→ P2（非核心异常，工作时间）→ P3（预警，汇总报告）

**CI/CD 与发布策略：**
- 持续集成：代码提交 → Lint → 单元测试 → 构建 → 镜像推送（GitHub Actions / GitLab CI）
- 持续部署：Feature Flag 控制灰度发布（LaunchDarkly / 自建），蓝绿部署或金丝雀发布
- 数据库迁移：向前兼容迁移策略（先加列 → 再迁移数据 → 再删旧列），Alembic（Python）/ Flyway（Java）
- 环境管理：Dev → Staging → Pre-production → Production 四环境标准

**灾备与业务连续性：**
- RTO/RPO 定义：核心服务 RTO < 1小时，数据 RPO < 1小时；分析服务 RTO < 4小时
- 数据备份：全量备份（每日）+ 增量备份（每小时），保留周期 30 天
- 跨可用区部署：服务层无状态多可用区，数据库主从跨可用区
- 降级策略：触达引擎降级（暂停低优先级活动，保障高优先级）、分析引擎降级（返回缓存数据）

**测试策略：**
- 单元测试：核心业务逻辑覆盖率 > 80%（人群圈选规则引擎、旅程状态机、频控逻辑）
- 集成测试：渠道适配器集成测试（Mock 外部 API）、多租户数据隔离测试
- E2E 测试：关键用户旅程自动化（创建活动 → 配置人群 → 选择渠道 → 发布 → 查看效果）
- 性能测试：压测场景（批量触达 100 万用户、人群圈选千万级 Bitmap 运算、旅程引擎 10 万并发状态转移）

**开发者体验：**
- API 文档：OpenAPI 3.0 规范 + 交互式文档（Swagger UI / Redoc）
- SDK 设计：统一 API 风格（RESTful + 统一错误码 + 分页规范），Web/移动/小程序/服务端四端 SDK
- API 版本管理：URL 路径版本（/v1/xxx），向后兼容策略（新版本发布后旧版本至少维护 12 个月）
- Sandbox 环境：供客户开发者测试 API 集成的沙箱环境（独立租户，预置测试数据）

### 跨维度补充

**产品成功指标（KPI）：**
- 产品级：DAU/MAU、客户 NPS、ARR/MRR、LTV/CAC、Logo Retention Rate
- 模块级北极星指标：
  - CDP 模块 → 活跃数据源数 / 客户、标签覆盖率
  - 旅程编排模块 → 活跃旅程数 / 客户、旅程完成率
  - 渠道管理模块 → 月触达量 / 客户、触达成功率
  - 人群圈选模块 → 人群包创建频率、圈选 → 触达转化率

**风险评估：**
- 技术风险：实时计算引擎稳定性（Flink 作业反压/Checkpoint 失败）、多租户数据泄露（RLS 配置遗漏）
- 市场风险：CRM/CDP 巨头下沉竞争（Salesforce/HubSpot 中国市场扩张）、客户付费意愿不及预期
- 合规风险：数据跨境传输（GDPR + 个保法双重约束）、用户隐私（Cookie 退役后的数据采集策略）、广告法合规（敏感词库维护成本）

  - 旅程引擎小队（2 后端 + 1 前端）
  - 渠道触达小队（2 后端 + 1 前端）

- 外部资源：UI 视觉设计师（外包）、渠道对接专员（按需）

**时间线与里程碑：**
- Alpha（内部测试）：MVP 3 模块可用，种子客户内测 → 预计 3-4 个月
- Beta（封闭测试）：5-10 个种子客户使用，核心流程跑通 → 预计 5-6 个月
- GA（正式发布）：功能稳定、文档完善、Onboarding 流程就绪 → 预计 8-10 个月

## 自查：批判性审查

### 一、方法论缺陷

**1. 投票矩阵是模拟的，不是真实的**
- 对等协作模式的核心价值在于三方独立判断后碰撞。实际执行中 PM/Designer/Engineer 三个 agent 独立收集事实，但 Round 2 并未真正交叉评论。投票矩阵由 Team Lead 模拟，非三方独立投票。
- 影响：共识和分歧的可信度打折，真实的三方投票可能产生不同的分歧点。

**2. Round 1 "事实"混入了估算和观点**
- 技能要求 Round 1 "只写事实，不评价"，但以下内容并非事实：
  - "PC 占 65-80%" — 多报告综合估算，非单一权威数据
  - "中国市场 MarTech 约 800-1200 亿元" — 不同机构口径差异大，范围过宽
  - "标准实施 1-3 月" — 行业惯例，非可验证事实
  - 竞品功能"强/中/弱"评级 — 主观判断，非事实
- 修正：应明确区分"有来源的数据点"和"行业共识/估算"。

**3. 补充 17 项遗漏说明初始审查不充分**
- 三个 agent 遗漏了 Onboarding、可观测性、CI/CD、KPI、风险评估、团队拓扑等基础项。这些不是边角料，是产品规划的必要组成部分。
- 根因：agent prompt 偏向垂直视角（技术/设计/产品），缺少水平视角（项目管理/工程实践）。

---

### 二、产品逻辑问题

**4. "MVP 聚焦 3 模块"根本不是 MVP**
- CDP（多渠道采集 + 身份合并 + 统一画像 + 人群分群 + 标签体系）= 一整个产品
- 营销自动化（旅程编排 + 触发 + A/B 测试 + 线索评分 + 频控）= 一整个产品
- 渠道管理（短信 + 邮件 + 推送 + 微信 + 小程序 + 社交媒体 + 广告平台）= 一整个产品
- 3 个"模块"各自都是独立 SaaS 产品的体量。所谓"MVP"实际上是"三合一产品线"。
- 真正的 MVP 应该是：一个细分场景的完整闭环。例如"电商场景的用户生命周期触达"—— 采集用户行为 → 圈选流失用户 → 自动发送优惠券 → 追踪转化。

**5. "待定"项才是最关键的决策**
- 首版切入行业、部署模式、技术栈选型 — 这些是所有后续工作的前提
- 画布把它们放在最后的"待定"区域，而把"MVP 模块切分"放在 P0
- 逻辑颠倒：不先确定行业和部署模式，怎么切分 MVP？电商零售的 MVP 和 B2B SaaS 的 MVP 完全不同。
- 修正：待定项应提升为 P0 前置项，在任何模块切分和技术设计之前完成。

**6. 28 项行动计划 = 没有优先级**
- P0 5 项 + P1 8 项 + P2 10 项 + 待定 5 项 = 28 项
- P0 标注"高价值、低成本"，但 5 项合计 PM 需 6 周 + Engineer 需 2 周，不是低成本
- 真正的 P0 应只有 1-2 项："不做这个，其他一切都不能开始"的事项
- 修正：P0 应精简为"确定行业 + 确定部署模式 + 定义一个场景的 MVP 闭环"。

---

### 三、差异化空洞

**7. "AI-first"是空话**
- 2026 年每家 MarTech 厂商都声称 AI-first。画布说"竞品补丁式集成 vs 原生嵌入"，但没有回答：具体哪些 AI 能力是竞品做不了而我们能做的？
- NLG 文案模板生成 — OpenAI/Claude API 调用，任何竞品都能做
- 智能发送时间 — Braze Sage AI、HubSpot Send Time Optimization 均已有
- 没有真正的 AI 差异化故事
- 修正：需要回答"我们的 AI 能力在哪个具体场景下比竞品强 10 倍？"如果回答不了，AI 就不应作为差异化定位。

**8. "微信生态深度集成"说了等于没说**
- 致趣百川已以微信生态为核心卖点，服务了微软、腾讯云、AWS
- 画布说"非渠道之一而是原生能力"，但没有定义"原生"具体指什么：
  - 小程序内嵌营销页面？
  - 企业微信 SCRM 深度打通？
  - 视频号直播与营销自动化联动？
  - 微信支付与优惠券实时核销？
- 没有具体定义的"差异化"不是差异化
- 修正：需要列出微信深度集成的 3-5 个具体功能场景，并评估致趣百川是否已经覆盖。

**9. 技术架构是行业通用模板，没有独特性**
- Engineer 列出的技术栈（PostgreSQL + ClickHouse + Kafka + Flink + Redis + ES）是任何数据密集型系统的标准选型
- 没有回答：这个架构相比竞品（神策有成熟数据底座、Convertlab 有成熟 MA 引擎）的技术优势在哪里？
- "从零规划的技术选型自由度"是优势，也是劣势 — 竞品有 5-10 年生产验证，新项目没有
- 修正：技术差异化应聚焦在"我们能做到而竞品做不到的技术能力"，而非"我们用了什么技术栈"。

**10. 8-10 个月 GA 的时间线假设了不存在的团队**

- 修正：行动计划必须基于团队现状，而非理想团队配置。

**11. 成本估算缺乏基准**
- 行动计划中的"PM 2 周""Engineer 3 周"是人周估算，但没有对应人员成本

**MVP 场景：电商弃单挽回自动化**

> 一个场景、一条完整链路、可衡量 ROI、5 人团队可交付。

**业务场景描述：**

电商零售客户的核心痛点之一是购物车弃单率（行业平均 60-80%）。每挽回 1% 的弃单，直接转化为 GMV。MVP 聚焦这一个场景，做到"采集弃单事件 → 自动圈选弃单用户 → 延迟触发微信触达 → 追踪转化"的完整闭环。

**用户旅程（完整闭环）：**

```
用户加购未支付
    ↓ (事件采集: JS SDK)
系统记录弃单事件
    ↓ (延迟 30 分钟, 排除已支付)
自动圈选弃单用户
    ↓ (规则引擎: 简单条件匹配)
发送微信模板消息 (含专属优惠券)
    ↓ (渠道触达: 微信服务号)
用户点击链接 → 回到购物车 → 完成支付
    ↓ (转化追踪: 归因匹配)
查看挽回效果看板 (挽回率/GMV/ROI)
```

**MVP 功能清单（最小可行）：**

| 功能 | 范围 | 复杂度 |
|------|------|--------|
| 事件采集 SDK | JS SDK，埋点加购/弃单/支付 3 个事件 | 低 |
| 事件接收 API | RESTful 端点，接收并存储事件到 PostgreSQL | 低 |
| 规则引擎 | 条件匹配（弃单金额 > X 且 未支付时间 > 30min），无需可视化画布 | 中 |
| 微信模板消息 | 对接微信服务号模板消息 API，含优惠券链接 | 中 |
| 优惠券生成 | 简单优惠券表 + 核销逻辑，无复杂风控 | 中 |
| 转化归因 | 点击链接携带 utm 参数，匹配支付订单 | 低 |
| 效果看板 | 单页仪表盘：弃单数/触达数/挽回数/挽回 GMV/ROI | 中 |
| 租户管理 | 最小多租户：tenant_id 隔离 + 简单注册登录 | 中 |

**技术架构（极简版）：**

```
┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│  JS SDK     │────→│  FastAPI     │────→│ PostgreSQL  │
│ (事件采集)   │     │ (API + 规则) │     │ (事件+业务)  │
└─────────────┘     └──────┬───────┘     └─────────────┘
                           │
                    ┌──────┴───────┐
                    │   Redis      │
                    │ (延迟队列)    │
                    └──────┬───────┘
                           │
                    ┌──────┴───────┐     ┌─────────────┐
                    │  Celery      │────→│ 微信 API    │
                    │ (异步触达)    │     │ (模板消息)   │
                    └──────────────┘     └─────────────┘

前端: React + Ant Design (单页管理后台)
后端: Python FastAPI + SQLAlchemy
数据库: PostgreSQL (事件表 + 业务表)
缓存/队列: Redis (延迟队列实现定时触达)
任务: Celery (异步消息发送)
```

**技术栈决策依据：**

- 放弃 ClickHouse/Flink/Spark — MVP 数据量级在万级事件/天，PostgreSQL 完全胜任
- 放弃 Kafka — Celery + Redis 延迟队列足够处理弃单触达场景
- 放弃 Elasticsearch — 规则引擎用 SQL WHERE 条件匹配，无需全文检索
- 保留 FastAPI + PostgreSQL + Redis — 与用户现有技术栈一致，降低学习成本

**MVP 不做的事（明确排除）：**

- 不做可视化旅程编排画布 — 规则引擎用配置文件/简单表单
- 不做多渠道触达 — MVP 只做微信模板消息
- 不做人群圈选可视化 — SQL 条件匹配 + 预设模板
- 不做 A/B 测试 — 后续迭代
- 不做推荐引擎/ML — 后续迭代

### P1-5: MVP 技术架构

**数据库 Schema（10 张核心表）：**

| 表 | 用途 | 关键字段 |
|---|------|---------|
| tenants | 租户 | name, code, status, plan, config(JSONB) |
| users | 用户 | tenant_id, external_id, openid, unionid, phone, tags(JSONB) |
| events | 事件 | tenant_id, user_id, event_type, event_id, properties(JSONB) |
| rules | 规则 | tenant_id, event_type, conditions(JSONB), actions(JSONB), priority |
| campaigns | 活动 | tenant_id, rule_id, status, budget, spent |
| coupons | 优惠券模板 | tenant_id, type, value, min_amount, total_count, used_count |
| redemptions | 核销记录 | tenant_id, coupon_id, user_id, code, status, order_id |
| delivery_logs | 触达日志 | tenant_id, user_id, channel, status, error_code |
| trigger_logs | 触发日志 | tenant_id, rule_id, event_id, status, skip_reason |
| analytics_daily | 每日统计 | tenant_id, date, abandoned_cart_count, recovered_gmv, recovery_rate |

**API 端点（11 个模块，60+ 端点）：**
- 认证（5）、租户（7）、用户（7）、事件采集（5）、规则（9）、活动（9）、优惠券（8）、核销（5）、触达日志（5）、分析报表（6）、Webhook（6）

**事件采集 JS SDK：**
- 支持 16 种事件类型（page_view, product_view, add_to_cart, checkout_start, payment_success 等）
- 批量发送（batchSize=10, flushInterval=5s）+ sendBeacon 兜底
- 客户端去重（Set 1000 条）+ 服务端去重（Redis 24h TTL）
- 离线缓存（localStorage 5MB, 7 天过期）

**规则引擎：**
- JSONB 存储条件树，支持 and/or/not 嵌套
- 20 种运算符（eq, gt, contains, between, regex, within, not_within 等）
- 6 种动作类型（delay, check, send_message, issue_coupon, update_user, webhook）
- 执行流程：事件到达 → 匹配规则 → 冷却检查 → 触发次数检查 → 条件评估 → 执行动作链

**延迟触达方案：**
- Redis Sorted Set 延迟队列（score=触发时间戳, member=task_id）
- Celery 定时轮询（每分钟）+ 4 个队列（delay_processor, wechat_sender, coupon_issuer, analytics）
- 失败重试：指数退避，最多 3 次，5 分钟延迟重入

**微信对接：**
- access_token 管理：Redis 缓存 + 分布式锁（double-check）+ 提前 200 秒刷新
- 可重试错误码：-1, 40001, 40002, 42001, 45009, 61003
- 限流：滑动窗口 100 次/分钟/租户

**多租户隔离：**
- 共享数据库 + tenant_id 字段 + PostgreSQL RLS
- 应用层 ContextVar + 中间件自动注入
- JWT Token 包含 tenant_id，RS256 签名

**9 项关键设计决策（含 Tradeoff）：**

| 决策 | 选择 | 放弃 | 理由 |
|------|------|------|------|
| 事件存储 | PostgreSQL JSONB | ClickHouse | MVP 百万级够用，团队熟悉 |
| 消息队列 | Redis Sorted Set | Kafka | 10 万级/秒够用，无额外组件 |
| 规则引擎 | JSONB + 应用层 | Drools | 简单灵活，快速迭代 |
| 分析报表 | Celery 定时任务 | Flink | 分钟级够用，成本低 |
| 微信通知 | 模板消息 | 订阅消息 | 无需用户订阅，触达率高 |
| 数据隔离 | 共享 DB + RLS | DB per 租户 | 成本低，运维简单 |
| 认证 | JWT | Session | 无状态，支持多端 |
| 事件处理 | 异步 Celery | 同步处理 | 解耦，支持延迟触达 |
| 架构形态 | 单体模块化 | 微服务 | 5 人团队，快速迭代 |

2. **微信卡包优惠券闭环**（替代纯模板消息）— 优惠券同步微信卡包 → 消息内嵌卡包链接 → 自动核销 → ROI 回流，开发 3 周
3. **净 GMV 归因看板**（替代粗放统计）— 净挽回 GMV = 挽回 GMV - 券成本，区分"挽回订单"和"自然回购"，自动周报推送，开发 3 周

**竞品差异化定位：**

| 维度 | 神策/Convertlab/致趣百川 | 我们 |
|------|-------------------------|------|
| 上手门槛 | 高（需技术团队配合） | 低（填表式，非技术人员可用） |
| 定价 | 年费 5-30 万起 | 月费 299 + GMV 抽成，年化 0.36-2.16 万 |
| 弃单场景 | 需定制配置 | 开箱即用 |
| ROI 可见性 | 需定制看板 | 自动计算净 GMV + ROI |

**GTM 策略草案：**
- 种子客户：年 GMV 500-5000 万的中腰部电商（美妆/食品/母婴/服饰），有赞/微盟商家
- 获客渠道：有赞/微盟服务市场（OAuth 接入）+ 电商运营社群 KOL + SEO/SEM 长尾词
- 定价：入门版免费（5% GMV 抽成）→ 成长版 299/月（3%）→ 专业版 999/月（1.5%）

| **合计** | | **275-860** |

**定价可行性验证：**

| 场景 | 客户数 | 月均 GMV/客户 | 月收入 | 月成本 | 月利润 |

## P2 规划：MVP 之后的扩展阶段

> 前提：MVP（弃单挽回自动化）上线并验证 PMF 后，进入 P2 扩展阶段。
> 团队仍为 5 人以下，每个阶段聚焦 1-2 个方向，避免并行过多。

### P2 阶段划分

**P2-A：弃单挽回增强（MVP 后 1-2 个月）**

在 MVP 基础上深化弃单挽回能力，提升挽回率和客户粘性。

| # | 功能 | 来源 | 成本 | 价值 | 说明 |
|---|------|------|------|------|------|
| 1 | **防刷风控规则** | US-016 | 1 周 | 高 | 单用户领取上限、设备/IP 异常检测、自动暂停 + 告警 |
| 2 | **自动周报推送** | US-020 | 1 周 | 中 | 每周一自动生成效果周报，微信模板消息推送，含趋势 + Top 规则 + 优化建议 |
| 3 | **漏斗分析** | US-021 | 2 周 | 中 | 全链路漏斗（浏览→加购→弃单→触达→点击→支付），支持按规则/品类/时段下钻 |
| 4 | **小程序订阅消息** | US-012 | 2 周 | 高 | 小程序场景适配，订阅消息授权引导，自动判断用户来源选择最优渠道 |
| 5 | **规则效果对比** | US-019 | 1 周 | 中 | 2-5 条规则并排对比（挽回率/GMV/ROI），自动标注最优和待优化规则 |
| 6 | **A/B 测试（轻量版）** | 新增 | 2 周 | 高 | 同一弃单人群随机分组，测试不同消息文案/优惠券面额/等待时间，确定性哈希分桶 |

**小计：** 9 周，核心价值是提升挽回率（从 10% → 15%+）

---

**P2-B：多渠道触达（MVP 后 2-3 个月）**

从微信单一渠道扩展到多渠道，覆盖更多用户触点。

| # | 功能 | 成本 | 价值 | 说明 |
|---|------|------|------|------|
| 7 | **短信渠道** | 2 周 | 高 | 对接阿里云/腾讯云短信网关，支持短信模板 + 短链接，作为微信未关注用户的补充渠道 |
| 8 | **邮件渠道** | 2 周 | 中 | 对接 SendGrid/SES，支持 HTML 邮件模板，适合高客单价场景（如美妆、奢侈品） |
| 9 | **App Push 渠道** | 2 周 | 中 | 对接极光/个推/UniPush，支持 App 内推送，适合有独立 App 的商家 |
| 10 | **智能渠道选择** | 2 周 | 高 | 根据用户画像自动选择最优触达渠道（关注公众号→微信，未关注→短信，有 App→Push），提升整体触达率 |
| 11 | **渠道效果归因** | 1 周 | 中 | 按渠道维度统计送达率/点击率/挽回率，辅助运营决策 |

**小计：** 9 周，核心价值是触达率从 75% → 90%+

---

**P2-C：高级分析与智能（MVP 后 3-5 个月）**

引入数据驱动的智能能力，从"规则触达"升级为"智能触达"。

| # | 功能 | 成本 | 价值 | 说明 |
|---|------|------|------|------|
| 12 | **用户分群** | 3 周 | 高 | 基于弃单行为/消费金额/频次自动分群（高价值/低价值/新客/沉睡），支持自定义标签 |
| 13 | **流失预测（轻量版）** | 3 周 | 中 | 基于历史弃单数据训练简单模型（逻辑回归），预测用户流失概率，高流失概率用户优先触达 |
| 14 | **智能发送时间** | 2 周 | 高 | 分析用户历史活跃时段，自动选择最佳发送时间（而非固定延迟），提升打开率 |
| 15 | **LTV 预估** | 2 周 | 中 | 基于历史数据估算用户生命周期价值，辅助优惠券面额决策（高 LTV 用户给更大优惠） |
| 16 | **队列分析** | 2 周 | 中 | 按注册/首次弃单时间分组，追踪不同队列的长期挽回率和 GMV 贡献 |

**小计：** 12 周，核心价值是从"被动挽回"升级为"主动预防"

---

**P2-D：团队协作与开发者体验（MVP 后 4-6 个月）**

支持多角色协作和开放生态，为规模化做准备。

| # | 功能 | 成本 | 价值 | 说明 |
|---|------|------|------|------|
| 17 | **多成员与权限** | 2 周 | 高 | 角色体系（管理员/运营/查看者）、操作权限控制、邀请流程 |
| 18 | **操作日志审计** | 1 周 | 中 | 记录谁在什么时间做了什么操作（规则变更/优惠券发放/配置修改），合规必备 |
| 19 | **OpenAPI 文档** | 1 周 | 中 | Swagger UI + 交互式文档，供客户开发者集成 |
| 20 | **Webhook 回调** | 1 周 | 高 | 弃单/触达/挽回事件通过 Webhook 推送到客户系统，支持 HMAC-SHA256 签名 |
| 21 | **API SDK** | 2 周 | 中 | Python/Node.js/Java 三端 SDK，封装事件采集和管理 API |
| 22 | **Sandbox 环境** | 1 周 | 中 | 供客户开发者测试 API 集成的沙箱环境，预置测试数据 |

**小计：** 8 周，核心价值是开放生态 + 合规能力

### P2 总体时间线

```
MVP 上线 (第 8 周)
    │
    ├── P2-A: 弃单挽回增强 (第 9-17 周, 9 周)
    │     重点: 防刷风控 + A/B 测试 + 小程序适配
    │
    ├── P2-B: 多渠道触达 (第 18-26 周, 9 周)
    │     重点: 短信 + 智能渠道选择
    │
    ├── P2-C: 高级分析与智能 (第 27-38 周, 12 周)
    │     重点: 用户分群 + 智能发送时间 + 流失预测
    │
    └── P2-D: 协作与开放 (第 39-46 周, 8 周)
          重点: 多成员权限 + Webhook + SDK
```

**总计：** P2 阶段约 38 周（9.5 个月），可与 P2-A/B 并行推进以压缩到 6-7 个月。

### P2 优先级建议（5 人团队）

不建议 4 个方向并行。推荐按以下顺序串行推进：

1. **P2-A**（必做）— MVP 的自然延伸，客户上线后立即需要的能力
2. **P2-B 仅短信渠道 + 智能渠道选择**（推荐）— 触达率是核心指标，短信是微信的重要补充
3. **P2-D 仅多成员权限 + Webhook**（推荐）— 规模化客户的刚需
4. **P2-C 智能发送时间**（推荐）— ROI 提升最明显，技术实现相对简单
5. 其余功能根据客户反馈按需推进

### P2 明确不做（延续 MVP 排除清单）

- 不做可视化旅程编排画布 — 填表式配置已验证有效
- 不做内容管理/DAM — 非弃单场景核心需求
- 不做广告平台对接（RTB/DSP）— 通过 Webhook 让客户自行对接
- 不做客服系统集成 — 通过 Webhook 对接第三方客服
- 不做供应链营销 — 非核心能力
- 不做线下 POS — 通过集成实现
