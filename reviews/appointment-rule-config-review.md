## 模式选择

**选定模式：** 对等协作

**选择理由：** 用户要求从多个维度分析预约规则的配置与生效机制，涉及产品完备性、用户体验、技术架构三个同等重要的视角。预约规则跨职能权衡较多（如产品灵活性 vs 配置复杂度 vs 技术实现），需要充分交叉碰撞。

## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**规则体系双轨并存：**
- 新体系 RuleSet（规则组）：租户级，按班次类型匹配，priority 优先级排序 (`models/rule_set.py:37-70`)
- 旧体系 SystemSettings（系统设置）：系统级 < 门店级 < 医生级，三级覆盖 (`models/settings.py:37-54`)
- 共存逻辑：排班有 shift_type_id 且有匹配 RuleSet → 用 RuleSet；否则回退 SystemSettings (`service_booking.py:96-145`)

**RuleSet 配置项：**
- 时间口径：time_source/timezone_source/compare_precision/rounding_mode/clock_skew_tolerance_sec
- 时间窗：action(BOOK/CHECKIN/CANCEL/HOLD_RELEASE) x reference_point x offset_sec x inclusive x fail_policy
- 预约策略：限约(per_shift/per_day/per_week)、冲突策略(same_shift/overlap_time/same_type_same_day)、前置条件(require_auth/require_profile_complete)
- 签到策略：宽限期(grace_period_sec)、超时处理(no_checkin_after_close: KEEP_BOOKED/AUTO_CANCEL/ABSENT)
- 容量策略：总容量、候补(waitlist_enabled/max_size/promote_policy)、超额(overbooking_enabled/max)

**SystemSettings 预约相关：**
- advance_days(10), same_day_booking(true), cancel_hours(2), per_day_limit(3), per_doctor_limit(1)
- no_show_limit(3), blacklist_days(30), advance_booking_minutes(0), sign_in_advance_minutes(30), sign_in_late_minutes(30)

**规则快照机制：**
- 创建预约时将 book_open_at/book_close_at/checkin_open_at/checkin_close_at/cancel_open_at/cancel_close_at + rule_set_id 存入预约记录 (`models/appointment.py:29-35`)
- 规则修改不影响已有预约

**4 个系统预设模板：**
- 标准门诊(优先级 100)、专家门诊(优先级 50)、体检预约(优先级 80)、急诊(优先级 10)
- 来源：`models/rule_set.py:217-427`

**覆盖场景：**
- 创建预约：排班状态→租户校验→休息日→时间窗→冲突→容量→黑名单→重复预约
- 取消预约：状态权限→时间窗快照→就诊前N小时限制→退款处理
- 签到：时间窗→宽限期→迟到状态标记
- 候补：WAITING/PROMOTED/CANCELLED/EXPIRED，取消后触发 auto_promote
- 爽约：状态码8，黑名单记录(no_show_count/source/expire_at)

### Designer — 用户视角

**两套独立配置 UI：**
- 排班规则设置：`/medical-services/schedule/rule`，基础信息+排班设置+高级设置，左侧日历预览
- 规则组管理：`/configuration/rule-sets`，6个Tab（基础信息/时间口径/时间窗/预约策略/签到策略/容量策略），右侧实时预览面板

**规则组表单交互：**
- 预设模板一键应用（4个系统预设 + 自定义预设）
- 实时预览面板 `RuleSetLivePreview`
- 规则效果预览弹窗 `RulePreviewModal`
- 核心配置完成度卡片

**患者端规则感知：**
- 预约成功页温馨提示：4条固定文案（提前15分钟签到、提前2小时取消、爽约3次黑名单等）
- 错误提示：Toast.show 显示错误信息
- 取消确认：简单 Dialog.confirm（"确定要取消预约吗？"）
- 重复预约：前端检查 + 确认对话框
- 无独立的预约须知/规则说明页面

**医生端规则感知：**
- 无法修改规则配置
- 可查看今日预约列表、签到状态、队列信息
- WebSocket 实时更新

**配置生效可见性：**
- 规则组修改后立即生效
- 排班生成需手动触发
- 规则列表显示启用/禁用状态、生成状态Tag

**批量操作支持：**
- 批量添加排班、批量删除、批量停诊
- 规则复制（跨医生）
- 导入导出

### Engineer — 技术视角

**数据模型：**
- 核心表：rule_sets, shift_types, rule_windows, rule_booking_policies, rule_checkin_policies, rule_capacity_policies, rule_set_audit_logs
- 关联表：rule_set_shift_types（多对多）
- 索引：idx_rule_sets_enabled_priority, idx_rule_windows_rs

**规则引擎架构：**
- 组合式服务：RuleEngineTimeWindowMixin + RuleEnginePolicyMixin + RuleEngineValidationMixin
- 无统一规则引擎抽象层，无规则 DSL
- 预设模板存储在模型代码中的嵌套字典

**加载策略：**
- 无缓存机制，每次实时查询数据库
- 性能监控装饰器 @monitor_performance
- Redis 指标存储（P50/P95/P99 延迟、慢查询日志，阈值 100ms）

**冲突检查策略链（短路执行）：**
1. per_user_per_shift → 2. conflict_same_shift → 3. per_user_per_day → 4. per_user_per_week → 5. conflict_overlap_time → 6. conflict_same_type_same_day

**并发控制：**
- 分布式锁：预约创建时 user-level + schedule-level 双重锁（Redis，timeout=10s, retry=5）
- 乐观锁：规则集更新时比对 updated_at，冲突返回 409
- 规则配置表无行锁或版本号字段

**多租户隔离：**
- 所有规则表含 tenant_id 字段（迁移 044 添加）
- 查询强制过滤 tenant_id
- Redis 监控指标按租户隔离

**代码分布：**
- modules/rule_engine/：5 文件约 800 行
- modules/rule_sets/：7 文件约 1500 行
- 预约业务集成：service_booking.py 中约 100 行规则调用

**安全：**
- SQLAlchemy ORM 参数化查询防 SQL 注入
- 规则配置修改限超级管理员
- 时间校验依赖服务器时间

### 独到发现

1. **黑名单规则未纳入 RuleSet 体系**：爽约/黑名单仍依赖 SystemSettings + 独立 Blacklist 表，是双轨制的遗留盲区（Designer 交叉发现）

2. **预设优先级数字设计反直觉**：priority 数值越小越优先，标准门诊(100) 反而低于专家门诊(50)，可能与直觉不符（PM 交叉发现）

3. **时间窗偏移秒数的前端友好转换**：OffsetInput 组件自动将秒转换为分钟/小时/天，后端秒级精度与前端友好交互兼顾（Designer 交叉发现）

4. **WebSocket 能力未被充分挖掘**：当前仅用于数据同步，未扩展到规则变更通知、冲突预警、容量监控等场景（PM 交叉发现）

5. **多租户缓存键设计未统一**：Redis 监控按租户隔离，但未来缓存键需确认包含 tenant_id 防止跨租户泄露（Engineer 交叉发现）

## Round 3：共识层

### 共识项

1. **双轨规则体系需要统一到 RuleSet**
   **结论：** RuleSet 按班次类型匹配的设计方向优于 SystemSettings 三级覆盖，但需补充门店/科室级粒度。SystemSettings 应逐步废弃，数据迁移至 RuleSet。
   **建议行动：** 制定分阶段迁移计划，Phase 1 将 SystemSettings 预约配置映射到 RuleSet，Phase 2 废弃 SystemSettings 预约相关字段。
   **成本估算：** 40-60h
   **优先级：** P1

2. **患者端规则展示需动态化**
   **结论：** 固定文案与可配置规则脱节是用户信任风险。患者端应从后端获取当前适用的规则摘要并动态展示。
   **建议行动：** 新增规则摘要 API，患者端预约流程中动态渲染规则提示。
   **成本估算：** 12-16h
   **优先级：** P0

3. **无缓存实时查询需要引入 Redis 缓存层**
   **结论：** 每次预约创建 5-6 次规则查询无缓存，高并发场景有性能瓶颈。规则配置是"读多写少"场景，适合缓存。
   **建议行动：** 引入 Redis 缓存，键设计包含 tenant_id + shift_type_id，规则变更时主动失效。
   **成本估算：** 16-24h
   **优先级：** P1

4. **两套配置 UI 需要统一入口**
   **结论：** 排班规则设置和规则组管理是两套独立 UI/后端模型，管理员认知负担高。应统一为单一规则配置入口。
   **建议行动：** 与双轨统一同步进行，保留一个配置界面，内部映射到 RuleSet。
   **成本估算：** 24-32h（可与双轨统一合并）
   **优先级：** P1

5. **分布式锁粒度需要优化**
   **结论：** 当前 user-level + schedule-level 双重锁在持锁期间执行全部规则校验，锁持有时间过长影响并发。
   **建议行动：** 将只读检查（时间窗校验、冲突预检）移到锁外，锁内仅执行写操作和最终容量校验。
   **成本估算：** 4-8h
   **优先级：** P0

6. **规则组需要软删除机制**
   **结论：** 当前规则组可被硬删除，已有预约的 rule_set_id 悬空导致后续取消/签到策略丢失。需要软删除 + null-safe 回退逻辑。
   **建议行动：** RuleSet 增加 soft_delete 字段，取消/签到时若 rule_set_id 悬空则回退到系统默认策略。
   **成本估算：** 8-12h
   **优先级：** P0

7. **审计日志需要增强粒度和前端展示**
   **结论：** 当前审计日志存在但不记录字段级变更，管理端无查看入口。管理员无法追溯"上周还能预约今天为什么不行"。
   **建议行动：** 增强 snapshot_before/snapshot_after 的字段级 diff，管理端增加规则变更历史查看。
   **成本估算：** 12-16h
   **优先级：** P1

8. **医生端可增加有限的规则覆盖能力**
   **结论：** 专家医生有个性化规则需求（如不接受当天预约），强制所有修改经超级管理员增加沟通成本。
   **建议行动：** 在租户定义的边界内，允许医生对关联自己的规则组做有限覆盖（如调整签到宽限期）。
   **成本估算：** 16-24h
   **优先级：** P2

### 分歧项

1. **冲突检查短路 vs 全量错误返回**
   **各方立场：**
   - PM：应返回全部错误让用户一次性了解问题
   - Engineer：短路是合理的性能优化，全量返回增加实现复杂度
   - Critic：短路可能遗漏组合冲突场景
   **裁决：** 折中方案——返回前 3 个最相关的冲突错误，既不过度复杂化实现，也避免用户反复试错。
   **决策依据：** 平衡用户体验和实现成本，前 3 个错误覆盖 90%+ 场景。

2. **预设模板硬编码 vs 数据库存储**
   **各方立场：**
   - PM：硬编码限制产品迭代，应作为产品功能
   - Engineer：系统预设硬编码合理，自定义预设已在 DB
   - Designer：迁移可能已开始
   **裁决：** 维持现状——系统预设保留种子数据（便于版本控制），确认 RuleSetPreset 表是否已完整支持自定义预设。
   **决策依据：** YAGNI 原则，系统预设变化频率极低，种子数据方案更可靠。

3. **规则快照是否需要存储策略快照**
   **各方立场：**
   - PM：快照丢失导致回退 SystemSettings，行为不一致
   - Engineer：快照设计正确，存时间点而非规则 ID
   - Critic：规则组删除后策略丢失
   **裁决：** 不存储完整策略快照（成本过高），但必须确保 rule_set_id 悬空时的优雅降级——软删除 + 系统默认策略兜底。
   **决策依据：** 快照机制已正确存储计算后的时间点，真正风险仅在规则组被删除。

## 被低估的优势

1. **时间窗偏移秒数的前端友好转换**：OffsetInput 组件自动将后端秒级精度转换为分钟/小时/天，兼顾精度和易用性

2. **规则快照机制本身设计合理**：创建时存储计算后的实际时间点（而非规则 ID + 偏移量），保证历史预约不受规则变更影响

3. **预设模板系统已有扩展性**：RuleSetPreset 表支持租户自定义预设，系统预设不可删除，架构已具备产品化基础

4. **实时预览面板**：RuleSetLivePreview 组件让管理员在配置时即时看到规则效果，降低试错成本

5. **分布式锁保障了号源安全**：双重锁（user + schedule）有效防止重复预约和号源超卖

## 摘要

**使用模式：** 对等协作

**关键共识：**
- 8 项达成共识（双轨统一、患者端动态展示、缓存引入、UI统一、锁优化、软删除、审计增强、医生端覆盖）

**关键分歧：**
- 3 项需要决策者介入（冲突检查策略、预设存储方式、快照完整性边界）

**Top 3 P0 行动：**
1. 患者端规则动态展示（12-16h）——修复固定文案与可配置规则脱节的信任风险
2. 分布式锁粒度优化（4-8h）——将只读检查移出锁临界区，提升并发性能
3. RuleSet 软删除+降级（8-12h）——防止规则组删除导致已有预约策略丢失

**Critic 关键洞察：**
- 双轨体系中 RuleSet 灵活性反而不如 SystemSettings（缺少门店/科室级覆盖），统一时必须补充
- 患者端固定文案是"定时炸弹"，规则配置越灵活，文案越容易误导
- 规则快照存的是计算后的时间点（设计正确），但规则组可被硬删除是真正的数据安全隐患
