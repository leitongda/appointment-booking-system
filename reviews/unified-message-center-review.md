## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**产品定位：**
- 系统定位为"提供订阅到期提醒、用量警告、欠费通知等功能"（`infrastructure/notifications/service.py:2-4`）
- 核心功能：统一消息分发、多渠道通知、消息收件箱、通知日志、配额管理、重试、去重

**功能完成度（15 项，12 已实现，3 部分实现）：**
- 已实现：消息模板管理、消息类型管理、接收人规则、多渠道发送、发送记录、失败重试、已读/未读、偏好设置、静默时段、配额管理、去重机制、消息统计
- 部分实现：审批/待办通知（仅请假审核）、WebSocket（仅 Doctor 端）
- 已实现：公告广播

**消息类型枚举：** appointment, consultation, schedule, system, stop_clinic, feedback + 渠道专用类型 appointment_success, appointment_reminder, appointment_cancelled, queue_call

**业务事件映射（15 个事件 → 渠道策略）：**
- 预约类（创建/提醒/取消）→ wechat + sms + in_app（三级降级）
- 叫号/排班 → websocket + in_app
- 停诊 → wechat + sms + in_app
- 请假审核 → in_app
- 平台公告 → 邮件 + 站内信
- 租户通知 → 邮件 + 短信 + 站内信

### Designer — 用户视角

**页面清单：** Admin 4 页 + Doctor 2 页 + Patient-H5 2 页，共 8 个通知相关页面

**交互模式：** 三端分页方式不同（ProTable/List/InfiniteScroll），已读标记一致（点击即读），全部已读确认不一致，删除均无二次确认

**WebSocket：** 仅 Doctor 端 4 个页面，心跳 25 秒，指数退避重连

**响应式/无障碍：** Patient-H5 移动端优先 + 屏幕阅读器支持；Admin 固定 400px；三端均有键盘导航 + ARIA

### Engineer — 技术视角

**存储层：** 7 张表（Message, MessageTemplate, NotificationLog, NotificationPreference, EmailTemplate, StoreEmailRecipient, TenantNotification），6 个 Migration

**核心引擎：** NotificationDispatcher（去重→渠道→偏好→静默→渲染→发送→日志）+ ChannelRegistry + BaseNotificationChannel

**渠道实现：** 5 个渠道（in_app/sms/email/wechat/websocket），模板存储分散 4 处，渠道串行发送

**任务队列：** 4 个 Celery 任务，三级预约提醒，指数退避重试

**配额：** 按渠道月度配额，租户自定义 > 订阅计划 > 默认

**安全：** JWT 认证，敏感数据明文存储，CSP/XSS/CSRF 未配置

**性能瓶颈：** 串行发送、独立 Redis 操作、dispatch() 内 db.commit()

### 独到发现

1. **[PM] 邮件未覆盖核心业务场景** — 邮件仅用于平台公告和租户通知，不涉及预约/叫号/停诊等核心场景，作为首个落地渠道验证价值有限
2. **[PM] 审批/待办与消息中心定位冲突** — 待办需要 due_at/completed_at 等字段和跳转处理页面的交互，与普通消息模型不匹配
3. **[PM] 消息偏好设置三端不一致** — Doctor 3 项渠道开关 vs Patient 5 项类型 + 3 项渠道，保存逻辑也不同（按钮提交 vs 实时保存）
4. **[Designer] 消息优先级缺失导致信息过载** — 紧急停诊和温和提醒混在一起，用户无法按重要性过滤
5. **[Designer] 静默时段无例外规则** — 紧急通知（如停诊）在静默时段内也被延迟，且用户不知道消息被延迟
6. **[Designer] 跨平台消息状态不同步** — 手机端标记已读后电脑端仍显示未读
7. **[Designer] 消息预览功能缺失** — 产品经理无法预览邮件在不同客户端的渲染效果
8. **[Engineer] 跨渠道发送日志去重缺失** — 同一事件多渠道发送产生多条日志，统计时重复计数
9. **[Engineer] 配额告警阈值硬编码** — 80%/90%/100% 不可配置，租户无法自定义

### Critic 质询

1. **[🚨 关键] 重构与补全的边界缺失** — 现有系统已有完整 5 渠道架构，"先实现全局消息系统再从邮件落地"到底是重构还是补全？没有方案对比和 ROI 分析

## Round 3：共识层

### ✅ 共识项

1. **议题：模板系统需统一**
   **结论：** 四种模板存储位置（MessageTemplate/EmailTemplate/system_settings/代码硬编码）导致维护成本高，需统一为单一模板引擎 + 统一存储
   **建议行动：** 统一为 Jinja2 模板引擎，通过渠道专用过滤器处理格式差异（微信固定 JSON 格式需二次包装）
   **成本估算：** 24-32 小时
   **优先级：** P1

2. **议题：消息类型枚举需重构**
   **结论：** 6 种数据库枚举 vs 10 种渠道类型 vs 15 个业务事件的映射关系混乱，需建立清晰的事件-类型-模板映射表
   **建议行动：** 重构为 event_type → template → channel_strategy 三层映射，支持子类型（如 appointment.success / appointment.reminder.24h）
   **成本估算：** 12-16 小时
   **优先级：** P1

3. **议题：安全机制需加固**
   **结论：** 邮件 HTML 模板 XSS 风险、敏感数据明文存储、CSP/CSRF 未配置，这三个问题在邮件作为首个落地渠道时必须先解决
   **建议行动：** Jinja2 autoescape=True + bleach 消毒；NotificationLog.recipient 脱敏；配置 CSP 白名单
   **成本估算：** 8-12 小时
   **优先级：** P0

4. **议题：站内信模板变量替换需实现**
   **结论：** dispatcher._render_content() 直接返回 event.title/content，未集成模板渲染
   **建议行动：** 集成 Jinja2 渲染逻辑到 _render_content()，支持 {{variable}} 语法
   **成本估算：** 4-6 小时
   **优先级：** P1（依赖模板系统统一）

5. **议题：用户反馈闭环需建设**
   **结论：** 无法评估通知效果（送达率、打开率、点击率），无法优化渠道策略
   **建议行动：** 增加用户互动事件（opened/clicked/dismissed），扩展统计维度
   **成本估算：** 12-16 小时
   **优先级：** P2

6. **议题：存储层和任务队列设计合理**
   **结论：** 三方一致认为现有 7 张表 + 4 个 Celery 任务的架构基础扎实，无需重构
   **建议行动：** 保持现有架构，在此基础上补全和优化
   **成本估算：** 0 小时
   **优先级：** 已确认

### ⚡ 分歧项

1. **议题：重构还是补全？**
   **各方立场：**
   - PM：12/15 功能已实现，核心差距在模板统一和事件映射
   - Engineer：NotificationDispatcher + ChannelRegistry 架构优良，扩展成本低（每渠道 4-6h）
   - Critic：无人证明"为什么需要重构"
   **裁决：** 用户决定**重构**。理由：模板系统碎片化、类型映射混乱、渠道实现不一致属于系统性设计问题，补全无法根治。重构可保留已被验证的优秀模式（Registry + DI），重新设计统一模型
   **决策依据：** 用户明确选择重构路线；CLAUDE.md 重构策略允许"完全替换内部结构"

2. **议题：邮件是否适合作为首个落地渠道？**
   **各方立场：**
   - PM：邮件仅覆盖边缘场景（平台公告/租户通知），不涉及核心业务
   - Engineer：EmailChannel 已实现，只需完善模板和安全（6-8h）
   - Critic：未直接评论
   **裁决：** 邮件作为首个落地渠道可行，但需调整渠道策略使其进入核心业务流程
   **决策依据：** 技术成本最低（已有实现），但需产品侧配合调整业务事件映射（预约成功/取消/停诊加入邮件渠道）

3. **议题：渠道串行发送是否需优化为并行？**
   **各方立场：**
   - PM/Designer：需并行，否则延迟累积
   - Engineer：需优化（8-12h）
   - Critic：降级逻辑下串行是设计意图，真实瓶颈在批量场景
   **裁决：** 分两步走 — (1) 降级场景保持串行（设计意图）；(2) 批量场景（如群发停诊通知）用 Celery 异步 + 分片处理
   **决策依据：** Critic 论据成立，降级场景串行是正确的；但批量场景是真实瓶颈

4. **议题：审批/待办是否独立于消息中心？**
   **各方立场：**
   - PM：应独立为"任务中心"，消息中心仅负责通知
   - Engineer：当前实现可复用，需 8-12h 扩展
   **裁决：** 独立。审批/待办有独特的交互需求（处理页面、截止时间、状态流转），强行塞入消息模型会增加复杂度
   **决策依据：** PM 的分析成立，Message 表增加 is_todo/due_at 等字段会破坏模型纯净性

5. **议题：去重策略是否需可配置？**
   **各方立场：**
   - PM：当前 24h 固定值合理
   - Designer：应按消息类型/优先级配置不同去重窗口
   **裁决：** 纳入消息优先级体系统一设计，P2 优先级
   **决策依据：** 当前 24h 去重覆盖大部分场景，可配置化可后续迭代

6. **议题：消息优先级是否需要？**
   **各方立场：**
   - PM：未评论
   - Designer：缺失导致信息过载，需 critical/high/medium/low 分级
   - Engineer：未评论
   **裁决：** 需要，但优先级为 P2。先完成核心消息中心改造，再引入优先级体系
   **决策依据：** 当前业务量级下信息过载问题不严重，优先解决模板统一和类型映射

## 复查修正（2026-05-14）

### 遗漏 1：接收人规则引擎 — 严重设计不足

用户将"接收人规则"列为消息中心顶层概念，但重构计划完全未涉及。

**现状：**
- 所有接收人硬编码在业务逻辑中（预约通知发 `appointment.user_id`，停诊查询受影响预约）
- 无接收人规则引擎
- 仅 3 种基础模式：业务关联（停诊查询受影响患者）、手动列表（批量发送）、事件订阅（门店邮件接收人）

**缺失的规则场景：**
- 按角色批量发送（"某科室所有医生"）
- 按科室/部门发送（"内科全体"）
- 动态规则（"预约了某时段的所有患者"）
- 继承规则（"通知科室主任时，同时通知该科室所有医生"）
- 条件规则引擎（"如果 A 则通知 B"）

**修正：** Phase 1 必须包含接收人规则引擎设计，否则"统一消息中心"无法覆盖核心场景。

### 遗漏 2：公告定位 — 被错误归类

用户将"公告"列为发送渠道之一，但实际上：

- 公告不是渠道（没有独立推送机制，不走 NotificationDispatcher）
- 公告不是消息类型（不存储在 messages 表中）
- 公告是独立的平台级租户通知子系统（独立表 tenant_notifications、独立 API、独立权限）
- 接收人维度是租户级（而非用户级）
- 支持定时发布（publish_at）、过期时间（expire_at）、优先级（priority）

**修正：** 重构时需决定：保持独立子系统（不纳入消息中心），或纳入消息中心作为特殊消息类型通过现有渠道推送。不能简单当作一个渠道。

### 遗漏 3：Message 与 NotificationLog 不应合并

重构计划提出"新建 UnifiedMessage 替代双表"，但两张表语义不同：

| 维度 | Message | NotificationLog |
|------|---------|-----------------|
| 职责 | 用户收件箱内容 | 渠道发送审计日志 |
| 粒度 | 每条通知 1 条记录 | 每条通知 × 每个渠道 1 条记录 |
| 独有信息 | is_read, read_at | channel, status, error_message, recipient, retry_count, sent_at |

合并会丢失：渠道追踪、重试管理、错误审计。一条通知发 3 个渠道时，Message 是 1 条，NotificationLog 是 3 条。

**修正：** 保持双表设计，统一其关联关系。Message (1) ← NotificationLog (N)。

### 遗漏 4：迁移策略 — 高风险未规划

至少 15 个调用点需要迁移：
- `appointments/service_booking.py` — 4 个调用点
- `appointments/service_flow.py` — 6 个调用点
- `schedule_suspensions/service.py` — 1 个调用点
- `schedules/service_generation.py` — 1 个调用点
- `schedules/service_mutation.py` — 2 个调用点
- `tasks/notification_task.py` — 直接创建 Message + NotificationLog（绕过 Dispatcher）
- `messages/service_messages.py` — 直接创建 Message + NotificationLog

**修正：** 重构必须规划迁移路径：新旧 API 兼容层、分阶段迁移、数据迁移脚本。

### 遗漏 5：10 项高级功能中 8 项未实现，重构计划未纳入

| 功能 | 状态 | 应纳入阶段 |
|------|------|-----------|
| 定时发送 | 未实现 | Phase 1（预约提醒依赖） |

### Phase 1：统一消息核心 + 邮件落地（68-92h）

1. **统一消息模型设计 + Migration（16-24h）**
   - 保留 Message 表（重命名/重构字段）：用户收件箱，is_read/read_at 管理
   - 保留 NotificationLog 表（重构字段）：渠道发送审计，channel/status/error_message/retry_count
   - 统一关联：Message (1) ← NotificationLog (N)，通过 notification_group_id 关联
   - 新建 EventTemplateMapping 表（替代 _DEFAULT_CHANNEL_STRATEGY 硬编码）
   - 新建 ChannelStrategy 表（渠道策略配置化：降级/并行/全发）
   - 新建 RecipientRule 表（接收人规则引擎）
   - 数据迁移脚本：旧表 → 新表

2. **统一模板引擎（16-20h）**
   - 新建 UnifiedTemplate 表（替代 MessageTemplate + EmailTemplate + system_settings 分散存储）
   - Jinja2 统一渲染引擎，autoescape=True
   - 渠道过滤器：
     - 邮件：HTML 输出
     - 短信：纯文本 + 字数截断
     - 微信：Jinja2 → {"key": {"value": "val"}} 二次包装
     - 站内信：纯文本
   - 模板预览 API（接受 template_code + 变量，返回渲染结果）
   - bleach 消毒 HTML 模板

3. **接收人规则引擎（12-16h）** ★ 新增
   - RecipientRule 模型：规则类型（role/department/user_list/dynamic/custom）
   - 规则解析器：将规则定义转换为用户 ID 列表
   - 预置规则：按角色（all_doctors/all_patients）、按科室、按用户列表
   - 动态规则：通过 SQL 条件查询（如"预约了某时段的所有患者"）
   - Admin 端接收人规则配置页面
   - 事件-规则绑定：每个事件类型可绑定默认接收人规则

4. **事件路由器 + 渠道策略配置化（12-16h）**
   - EventRouter 替代 NotificationDispatcher（保留 Registry + DI 模式）
   - event_type 三层映射：event → template → channel_strategy
   - 支持子类型：appointment.success / appointment.reminder.24h / appointment.cancelled
   - 渠道策略：降级模式/并行模式/可配置
   - 去重策略可配置化：按事件类型设置去重窗口
   - Admin 端渠道策略配置页面

5. **邮件渠道重构 + 安全 + 退订（12-16h）** ★ 扩展
   - 基于 BaseNotificationChannel 重写 EmailChannel
   - 邮件模板统一使用 UnifiedTemplate
