## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**API 接口清单（17个端点）：**

规则组 CRUD：
- GET /rule-sets — 列表（分页+筛选：enabled, shift_type_id）
- GET /rule-sets/{id} — 详情
- POST /rule-sets — 创建
- PUT /rule-sets/{id} — 更新
- DELETE /rule-sets/{id} — 删除

状态控制：
- POST /rule-sets/{id}/enable — 启用
- POST /rule-sets/{id}/disable — 禁用

预览：
- POST /rule-sets/preview — 规则效果预览（支持 BOOK/CHECKIN/CANCEL 三种窗口）

性能监控：
- GET /rule-sets/performance — 性能统计（P50/P95/P99）
- GET /rule-sets/slow-queries — 慢查询列表
- DELETE /rule-sets/performance/metrics — 清除指标

时间窗：
- POST /rule-sets/{id}/windows — 创建
- PUT /rule-sets/windows/{id} — 更新
- DELETE /rule-sets/windows/{id} — 删除

策略（Upsert）：
- PUT /rule-sets/{id}/booking-policy
- PUT /rule-sets/{id}/checkin-policy
- PUT /rule-sets/{id}/capacity-policy

**数据模型（8个表）：**
- shift_types（code唯一），rule_sets（索引 enabled+priority），rule_set_shift_types（关联表）
- rule_windows（支持 BOOK/CHECKIN/CANCEL/HOLD_RELEASE），3个策略表（一对一）
- appointment_checkins（签到日志）

**前端功能：**
- 列表页：分页、筛选、批量操作、导入导出、侧边栏预览
- 表单页：6个Tab、4个预设模板、实时预览、核心配置完成度指示器
- 可视化组件：10个，共3338行

**权限模型：**
- 查询：普通管理员，修改：超级管理员
- 前端路由：canRuleSets = isSuperAdmin

**HOLD_RELEASE 动作类型：**
- 数据模型中合法（RuleWindow.action 注释包含）
- 前端 4 个组件完整支持（颜色、渲染）
- 后端消息映射有 "释放"
- 但无端到端业务流程使用，preview 只检查 BOOK/CHECKIN/CANCEL

### Designer — 用户视角

**埋点：** 10个函数

### Engineer — 技术视角

**后端架构：** Mixin组合模式，规则引擎5文件675行

**N+1查询（2处）：**
1. service_query.py — 列表查询对每条记录 refresh 加载4个关联（默认 page_size=10，影响有限）
2. service_mutation.py — update 逐个删除关联和 window

**高复杂度方法：**

## Round 3：共识层

### 共识项

1. **导入功能路由未注册（348行死代码）**
   - 结论：前端 ImportExport 按钮指向不存在的后端端点，用户体验 404
   - 行动：挂载 RuleSetImportService 到路由，或清理死代码+移除前端按钮
   - 成本：2-4h
   - 优先级：P0

2. **批量操作权限不对称**
   - 结论：批量启用/禁用按钮对非超管可见但逐个403，无友好反馈
   - 行动：前端用 access.canSuperAdmin 隐藏批量操作按钮（与批量删除一致）
   - 成本：2h
   - 优先级：P0

3. **文件头注释过时**
   - 结论：rule-set-form.tsx 头部注释声称"~800行"实际1548行
   - 行动：修正注释
   - 成本：0.5h
   - 优先级：P0

4. **前端重复逻辑统一抽取**
   - 结论：ACTION_COLORS(4处)、REFERENCE_POINT_LABELS(3处)、不限制判断(2处)、formatTime(GanttTimeline未用共享版)
   - 行动：提取到 constants/rule-set.ts 和 ruleSetFormatter.ts，删除各组件内联定义
   - 成本：4-6h
   - 优先级：P1

5. **双路径更新并发风险**
   - 结论：全量替换与增量更新双路径有竞态风险
   - 行动：短期文档化风险+添加乐观锁（updated_at版本号）；长期评估是否统一路径
   - 成本：6-8h
   - 优先级：P1

6. **check_booking_conflicts 策略链重构**
   - 结论：183行圈复杂度12-15，7个独立条件块，适合策略链模式
   - 行动：提取为策略列表+循环，每个检查项为独立策略函数，降低复杂度至2-3
   - 成本：8-12h
   - 优先级：P1

7. **N+1查询优化**
   - 结论：列表页每条记录 refresh 4个关联（默认10条），update 逐个删除
   - 行动：列表页在查询时 selectinload 所有关联（去掉 refresh）；update 用批量删除替代逐个删除
   - 成本：4-6h
   - 优先级：P1

8. **补充集成测试**
   - 结论：反映端到端验证缺失
   - 行动：补充规则组 CRUD + 导入导出 + 预览 的端到端集成测试
   - 成本：8-12h
   - 优先级：P1

### 分歧项

1. **HOLD_RELEASE 动作类型定位**
   - 现状：数据模型+前端完整支持，但无端到端业务流程
   - 选项：(A) 明确标记为"预留扩展点"，文档化 (B) 移除前端展示降低认知负担
   - 裁决：标记为"预留扩展点"，保留代码不动，等待产品确认是否纳入 roadmap
   - 决策依据：移除成本高且可能后续需要，标记即可
   - **2026-03-30 最终决策：保留为预留扩展点。** 经分析确认是精心设计的扩展点而非半成品（数据模型、前端配置、规则引擎三层均完整支持），等支付功能上线后可直接接入，无需改规则引擎。移除成本 > 保留成本。

2. **预设模板是否需要后端支持**
   - 现状：4个模板硬编码在前端 constants 中
   - 选项：(A) MVP可接受 (B) SaaS多租户应有后端模板管理
   - 裁决：当前阶段可接受，纳入 P2 规划
   - **2026-03-30 已完成。** 新增 `RuleSetPreset` 模型 + CRUD 路由 + lazy seed 4个系统预设 + 前端动态加载。

## 待定项决策记录（2026-03-30）

### HOLD_RELEASE — 保留为预留扩展点

经全链路代码分析，HOLD_RELEASE 是精心设计的扩展点：
- 数据模型层：迁移脚本、字段注释均包含，合法 action 值
- 前端配置层：颜色(ACTION_COLORS)、选项(WINDOW_ACTION_OPTIONS)、可视化渲染完整支持
- 规则引擎层：`check_action_window()` 支持任意 action，无硬编码限制
- 无半成品痕迹：无 TODO、无废弃代码、无未完成分支

当前无端到端业务流程使用（系统无支付功能），等支付功能上线后直接接入即可。移除反而增加未来恢复成本。

### 可视化组件视觉回归测试 — 不做

- 管理后台低流量页面（仅超级管理员使用），16-20h 投入无对应回报
- SVG 渲染测试需真实浏览器环境（Playwright/Cypress），基础设施搭建成本高
- 可视化组件已清理未使用导出（P2 完成），实际活跃组件仅 6 个
- 替代策略：改动时按需补充单元测试，不搞全局视觉回归
