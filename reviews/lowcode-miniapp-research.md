## 二、小程序代码生成技术方案

### 2.1 两条技术路径对比

| 路径 | 运行时渲染 (Runtime) | 编译时生成 (Codegen) |
|------|---------------------|---------------------|
| 原理 | Schema JSON → 运行时解释器 → 小程序渲染 | Schema JSON → AST/模板 → Taro 源码 → 编译 → 小程序 |
| 优点 | 即时预览，无需编译，动态更新 | 产物是标准 Taro 代码，可二次编辑，性能最优 |
| 缺点 | 运行时开销，组件能力受限于解释器 | 需要编译步骤，预览不够实时 |
| 代表方案 | amis (百度)、H5-Dooring | lowcode-engine (阿里)、自建 codegen |
| 适合场景 | 营销页、简单展示页 | 核心业务流程、复杂交互页 |

**推荐策略: 双模式并存**

- **简单页面**: 运行时 Schema 渲染，运营人员拖拽后即时预览
- **复杂页面**: 编译时生成 Taro 代码，开发人员可二次修改

### 2.2 Taro 框架的代码生成能力

根据 Taro 官方文档，Taro 提供了丰富的扩展点：

**插件系统** — Taro 支持三种插件类型：
- `plugin-command` — 扩展 CLI 命令
- `plugin-build` — 扩展编译流程（beforeBuild/afterBuild hooks）
- `plugin-template` — 自定义页面模板

**自定义平台插件** — 可以继承 `@tarojs/plugin-platform-weapp` 创建自定义平台：
```typescript
import { Weapp } from '@tarojs/plugin-platform-weapp'
export default class Example extends Weapp {
  platform = 'example'
  runtimePath = `@tarojs/plugin-platform-example/dist/runtime`
}
```

**模板系统** — `template_creator.js` 支持动态生成页面文件，可用于低代码平台的页面脚手架生成。

**结论**: Taro 的插件体系可以深度集成低代码平台的代码生成流程。

### 2.3 Schema DSL 设计建议

推荐采用类 JSON Schema 的声明式协议：

```json
{
  "componentName": "Page",
  "props": { "navigationBarTitleText": "预约挂号" },
  "children": [
    {
      "componentName": "NutButton",
      "props": { "type": "primary", "block": true },
      "children": [{ "componentName": "Text", "props": { "text": "立即预约" } }]
    }
  ],
  "dataBinding": {
    "appointments": { "api": "/api/appointments", "method": "GET" }
  }
}
```

关键设计原则：
- 组件名映射 NutUI 组件库，降低心智负担
- 支持数据绑定（API 调用、变量引用、事件链）
- 支持条件渲染和列表渲染的声明式表达
- 与现有 `@hospital/api` 包的数据请求层对接

## 三、主流开源低代码平台架构分析

### 3.1 平台对比矩阵

| 平台 | Stars | 小程序支持 | 拖拽编辑器 | 组件生态 | 扩展性 | 最近维护 | License |
|------|-------|-----------|-----------|---------|--------|---------|---------|
| **lowcode-engine** (阿里) | ~16k | 无原生支持 | 完整 | 需自建物料 | 极高 | 2024 停滞 | MIT |
| **H5-Dooring** | ~7k | 部分支持 | 完整 | 丰富(H5) | 中 | 活跃 | MIT |
| **amis** (百度) | ~17k | 不支持 | 无(纯JSON) | 120+组件 | 中 | 活跃 | Apache-2.0 |
| **Formily** (阿里) | ~11k | 不支持(Taro) | 表单专用 | 表单组件 | 中高 | 维护中 | MIT |
| **MicroApp** (京东) | ~5k | 不支持 | 不适用(微前端) | N/A | 高 | 活跃 | MIT |
| **Puck** | ~8k | 不支持 | 完整 | React组件 | 高 | 活跃 | MIT |
| **Pragmatic DnD** (Atlassian) | ~3k | 不适用 | 底层库 | N/A | 极高 | 活跃 | Apache-2.0 |

### 3.2 关键发现

**lowcode-engine (阿里)**
- 最完整的低代码引擎架构：Schema 协议 + 物料协议 + 搭建协议
- 提供两套正式协议规范："基础建设协议" 和 "物料协议"
- **致命缺陷**: 无小程序渲染器，仅有 React Simulator Renderer (Chrome >= 80)
- CDN 加载模型 (window.AliLowCodeEngine) 与 Taro 3 的模块化打包冲突
- v1.3.2 后无新 release，654 个 open issues，开发势头明显放缓
- **结论**: 架构理念值得借鉴，但直接集成不可行

**H5-Dooring**
- 使用 React DnD 作为拖拽引擎，JSON Schema 作为数据交换格式
- 支持 H5 页面和小程序页面的可视化搭建
- 插件化架构，支持 100+ 垂直平台的横向扩展
- **优势**: 最接近我们需求的开源方案，有小程序支持
- **劣势**: 组件生态偏营销场景，缺少医疗业务组件

**amis (百度)**
- JSON 配置驱动 UI，120+ 内置组件（表格、表单、图表等）
- 百度内部大规模验证，稳定性极高
- **劣势**: 纯 Web 方案，不支持小程序渲染；更适合后台管理系统
- **可用价值**: 其 JSON Schema 设计理念可借鉴到小程序 DSL 中

**Puck**
- 提供 `<Render>` 组件，编辑器输出可直接在运行时消费
- 编辑器与渲染器共享同一套 config+data，实现 WYSIWYG
- **劣势**: 仅支持 React，不支持 Taro/小程序

### 3.3 架构借鉴建议

没有一个现成的开源方案能直接满足"拖拽生成 Taro 小程序"的需求。推荐策略：

1. **借鉴 lowcode-engine 的协议设计** — 物料协议、搭建协议、渲染协议三层分离
2. **借鉴 H5-Dooring 的编辑器架构** — 插件化物料 + 拖拽搭建 + JSON Schema 输出
3. **借鉴 Puck 的渲染理念** — 编辑器输出与运行时渲染共享 Schema
4. **自建 Taro 渲染器** — 将 Schema 映射为 NutUI 组件树

## 四、拖拽引擎核心实现

### 4.1 拖拽库选型

| 库 | Stars | React 支持 | 触控支持 | 可访问性 | 多列排序 | 推荐度 |
|----|-------|-----------|---------|---------|---------|--------|
| **dnd-kit** | ~14k | React/Vue/Solid | 优秀 | 优秀 | 原生支持 | 强烈推荐 |
| **@hello-pangea/dnd** (react-beautiful-dnd 继任) | ~8k | React | 一般 | 优秀 | 支持 | 推荐 |
| **Pragmatic DnD** (Atlassian) | ~3k | 框架无关 | 良好 | 优秀 | 支持 | 推荐 |
| **sortablejs** | ~20k | 有 React 封装 | 良好 | 一般 | 支持 | 可选 |

**推荐: dnd-kit**

理由：
- 多框架支持 (React/Vue/Solid)，与项目未来可能的框架迁移兼容
- DragOverlay 组件支持自定义拖拽预览，适合搭建场景的实时预览
- Sensor 系统 (鼠标/触控/键盘) 兼容小程序触控操作
- SortableContext 原生支持多列排序，适合组件面板 → 画布的拖拽
- 409+ 代码示例，社区活跃，Benchmark Score 84.5

### 4.2 编辑器核心架构

```
┌─────────────────────────────────────────────────────┐
│                   低代码编辑器                        │
├──────────┬──────────────────────┬───────────────────┤
│ 物料面板  │       画布区域        │    属性面板        │
│ (左侧)   │     (中间/预览)       │    (右侧)         │
│          │                      │                   │
│ 组件列表  │  ┌────────────────┐  │  选中组件的        │
│ 模板列表  │  │  组件树渲染     │  │  属性配置表单      │
│          │  │  (Schema→React) │  │  数据绑定配置      │
│ [拖出]   │  │                │  │  事件配置          │
│    ↓     │  │  dnd-kit       │  │                   │
│ DragOverlay│ │  SortableContext│ │                   │
│          │  └────────────────┘  │                   │
├──────────┴──────────────────────┴───────────────────┤
│                  Schema State (Zustand)              │
│  { components: [...], dataBindings: {...}, ... }    │
├─────────────────────────────────────────────────────┤
│              代码生成器 (Codegen Layer)               │
│  Schema → Taro JSX 源码 / 运行时 Schema JSON         │
└─────────────────────────────────────────────────────┘
```

### 4.3 Schema 状态管理

推荐使用 **Zustand** 管理编辑器状态：

```typescript
interface EditorStore {
  // 组件树
  components: ComponentNode[];
  // 选中状态
  selectedId: string | null;
  // 撤销/重做
  history: HistoryStack;
  // 操作
  addComponent: (node: ComponentNode, parentId: string) => void;
  moveComponent: (id: string, newParentId: string, index: number) => void;
  updateProps: (id: string, props: Record<string, any>) => void;
  removeComponent: (id: string) => void;
}
```

### 4.4 实时预览方案

| 方案 | 优点 | 缺点 | 适合场景 |
|------|------|------|---------|
| **同页面 React 渲染** | 最快，无 iframe 开销 | CSS 隔离困难 | 编辑器内部预览 |
| **iframe 沙箱** | 完全隔离，样式不污染 | 通信复杂，性能开销 | 生产级预览 |
| **Shadow DOM** | 样式隔离，性能好 | 部分组件兼容问题 | 折中方案 |

**推荐**: 编辑器内用同页面渲染 (Schema → React 组件树直接渲染)，发布预览用 iframe。

### 4.5 组件协议设计

每个低代码组件需要定义：

```typescript
interface LowCodeComponent {
  // 唯一标识
  componentName: string;
  // 显示名称
  title: string;
  // 分类
  category: 'basic' | 'form' | 'business' | 'layout';
  // 图标
  icon: string;
  // 默认 props
  defaultProps: Record<string, any>;
  // 可配置属性 (属性面板用)
  configureSchema: PropertySchema[];
  // 渲染器 (Schema → React 组件)
  renderer: React.ComponentType<ComponentProps>;
  // Taro 渲染器 (Schema → Taro 组件)
  taroRenderer?: React.ComponentType<ComponentProps>;
  // 代码生成模板
  codeTemplate: string;
}
```

## 五、医疗SaaS低代码平台案例

### 5.1 商业平台对比

| 平台 | 厂商 | 小程序支持 | 多租户 | 私有化部署 | 价格参考 | 医疗案例 |
|------|------|-----------|--------|-----------|---------|---------|
| **微搭 WeDa** | 腾讯云 | 原生微信小程序 | ISV 多租户 | 支持 | ¥2,388/年起 | 挂号、健康管理 |
| **FinClip** | 自研 | 小程序容器(兼容微信) | 多租户管理 | 支持 | 按需报价 | 金融/医疗 App |
| **轻流** | 自研 | H5 为主 | 支持 | 专有轻流 | 按需报价 | 医院流程管理 |
| **简道云** | 帆软 | 不支持小程序 | 有限 | 支持 | ¥3,600/年起 | 表单数据管理 |

### 5.2 微搭 WeDa 详细分析

**核心能力**:
- 全生命周期管理：注册 → 授权 → 开发 → 预览 → 发布
- 同时输出 PC Web、H5、微信小程序
- ISV 多租户部署：一个平台账号服务多个客户，跨租户一键部署 + 数据隔离
- 效率提升声称：60%-150%，交付周期从数月缩短到数周

**定价**:
- 私有化部署: ¥2,388/年，不限 B 端用户数和应用数

**对我们的启示**:
- ISV 多租户模式正是我们"先内部后对外"路线的参照
- 但 WeDa 绑定腾讯云生态，定制化受限
- 我们需要的不仅是营销页，还有核心业务流程，WeDa 的表单驱动模式可能不够灵活

### 5.3 FinClip 详细分析

**核心能力**:
- 小程序容器 SDK — 任何 App 集成后即可运行小程序
- 高兼容微信小程序语法和生态
- 云原生架构，支持私有化部署

**对我们的启示**:
- 如果目标是让医院客户的 App 内嵌小程序，FinClip 是参考方案
- 但 FinClip 是容器方案而非搭建方案，不解决"如何生成小程序"的问题

### 5.4 多租户低代码平台架构模式

医疗SaaS低代码平台的多租户架构需要考虑：

```
┌─────────────────────────────────────────────┐
│              租户管理平台 (Admin)              │
│  租户注册 → 订阅管理 → 权限分配 → 模板市场    │
├─────────────────────────────────────────────┤
│              低代码编辑器 (共享)               │
│  搭建界面 → Schema 编辑 → 组件市场            │
├─────────────────────────────────────────────┤
│            租户隔离层                          │
│  Schema 存储隔离 | 数据源隔离 | 发布隔离       │
├─────────────────────────────────────────────┤
│            渲染/发布层                         │
│  Schema → Taro 编译 → 小程序包 → 审核发布     │
└─────────────────────────────────────────────┘
```

关键隔离点：
- **Schema 隔离**: 每个租户的页面 Schema 独立存储
- **组件隔离**: 租户可使用的组件集受订阅计划控制
- **数据源隔离**: API 调用自动注入 tenant_id
- **发布隔离**: 每个租户独立的小程序 AppID 和发布流程

## 六、自建 vs 集成 vs 采购 ROI 分析

### 6.1 三种路径对比

| 维度 | 自建低代码平台 | 集成开源方案 | 采购商业平台 |
|------|--------------|------------|------------|
| **初期投入** | 3-6 人月 (100-200万) | 1-2 人月 (30-60万) | 按年订阅 (2-10万/年) |
| **上线周期** | 4-8 个月 | 2-3 个月 | 1-2 个月 |
| **定制化能力** | 极高，完全可控 | 高，可二次开发 | 低，受平台限制 |
| **维护成本** | 高，需持续投入 | 中 | 低，供应商维护 |
| **技术栈匹配** | 完美匹配 Taro + NutUI | 需适配 | 可能不匹配 |
| **SaaS 输出** | 可作为产品对外输出 | 可包装输出 | 受供应商条款限制 |
| **风险** | 开发风险高，可能延期 | 开源项目可能停更 | 供应商锁定 |
| **长期 TCO** | 高（但可摊薄到 SaaS 收入） | 中 | 持续订阅费用 |

### 6.2 推荐路线图

**分三阶段实施，渐进式自建：**

#### Phase 1: MVP — 营销页面搭建 (2-3 个月)

**目标**: 运营人员能独立搭建营销/展示类页面

**技术选型**:
- 拖拽引擎: dnd-kit
- 编辑器框架: 自建 (借鉴 H5-Dooring 架构)
- Schema 存储: PostgreSQL (复用现有数据库)
- 组件库: NutUI React (Taro) 组件子集
- 渲染模式: 运行时 Schema 渲染

**交付物**:
- 可视化拖拽编辑器 (admin 后台内嵌)
- 10+ 基础组件 (文本、图片、按钮、轮播、表单等)
- 3-5 个医疗场景模板 (科室介绍、活动页、公告页)
- Schema → Taro 小程序的运行时渲染器
- 页面预览 + 一键发布到小程序

**预计工时**: 2-3 人月

#### Phase 2: 业务流程页面 (3-4 个月)

**目标**: 开发人员能搭建预约挂号等核心业务流程

**新增能力**:
- 数据绑定可视化配置 (对接 @hospital/api)
- 条件渲染 / 列表渲染的拖拽配置
- 自定义逻辑块 (代码片段插入)
- 编译时代码生成 (Schema → Taro JSX)
- 组件市场 (自定义组件注册)

**预计工时**: 3-4 人月

#### Phase 3: SaaS 化 + 外部输出 (3-4 个月)

**目标**: 作为独立产品提供给其他医院/机构

**新增能力**:
- 租户管理 + 订阅计划
- 模板市场 (模板的上传、审核、分发)
- 独立部署 + 数据隔离
- 小程序的独立 AppID 管理和发布流水线
- 组件/模板的版本管理

**预计工时**: 3-4 人月

### 6.3 总成本估算

| 阶段 | 人力成本 | 基础设施 | 合计 |
|------|---------|---------|------|
| Phase 1 | 15-25万 | 2-3万 | 17-28万 |
| Phase 2 | 20-35万 | 3-5万 | 23-40万 |
| Phase 3 | 20-35万 | 5-10万 | 25-45万 |
| **合计** | **55-95万** | **10-18万** | **65-113万** |

对比参考:

- 自建的 3 年 TCO 大约与采购持平，但拥有完整控制权和 SaaS 输出能力

## 八、技术栈推荐汇总

| 层 | 技术选择 | 理由 |
|----|---------|------|
| 拖拽引擎 | dnd-kit | 多框架、触控友好、SortedList 原生支持 |

| 代码生成 | 自建 Codegen | Schema → Taro JSX/TSX 源码 |
| 组件库 | NutUI React (Taro) | 与现有小程序技术栈完全一致 |
| 数据绑定 | 对接 @hospital/api | 复用现有 API 封装层 |
| Schema 存储 | PostgreSQL | 复用现有数据库，JSONB 字段存储 |
| 多租户 | 复用 TenantContext | 现有中间件 + Schema 层强制隔离 |

## 九、结论

1. **没有现成的"拖拽生成小程序"一站式方案** — 所有开源平台要么不支持小程序 (amis, Formily, Puck)，要么已停止维护 (lowcode-engine)，要么仅支持营销页 (H5-Dooring)
2. **自建是最可行的路径** — 基于现有 Taro + NutUI 技术栈，借鉴开源平台的架构理念，自建轻量级编辑器
3. **分阶段实施降低风险** — Phase 1 (营销页, 2-3月) → Phase 2 (业务流程, 3-4月) → Phase 3 (SaaS化, 3-4月)
4. **总投入约 65-113 万**，3 年 TCO 与采购商业平台持平，但拥有完整控制权
5. **核心差异化** — 深度集成医院预约挂号业务逻辑，这是通用低代码平台无法提供的

## 十、补充研究发现（深度验证）

### 10.1 唯一可用的 Taro 低代码搭建参考项目

**weilaiqishi/lowcode-designable-taro-react** (GitHub 66 星, 18 Fork)

- 架构：Designable (阿里) + Formily + NutUI React Taro
- 四个子包：editor (Designable+Formily 编辑器, rspack 构建)、mobile (Taro 运行时)、ui (14 个 NutUI 组件的 Formily 适配包装)、designable-formily-transformer (TreeNode 与 Schema 格式互转)
- **关键警告**: Designable 自 2021 年 8 月后停止维护（最后 release v0.5.19），该项目为 PoC 级
- **可借鉴点**: TreeNode 与 Schema 互转的核心思路仍有参考价值，但需要替换 Designable 为活跃维护的拖拽引擎（如 dnd-kit）
- **结论**: 无京东/美团等大厂的 Taro 低代码搭建公开实践；Taro 官方未提供过搭建相关的 RFC 或工具

### 10.2 Formily — 属性面板的理想选择

**Formily 分布式字段状态管理** (GitHub 12.5k 星, v2.3.6, 2025 年 5 月活跃维护)

- 核心解决：React 受控模式下表单全树重渲染的性能问题
- 技术实现：基于 `@formily/reactive` 的细粒度字段级响应式（类似 MobX）
- **对低代码平台的实际意义**: 右侧属性面板需要高频更新选中组件的属性配置表单，如果每次属性修改都触发整棵表单树重渲染，编辑器性能会显著下降
- **推荐用法**: 属性面板使用 Formily 管理配置表单，实现字段级独立更新
- **注意**: Formily 不支持 Taro/小程序原生渲染，但编辑器本身运行在 Web 环境，不受此限制

### 10.3 Taro 代码生成的三个工程陷阱

**陷阱 1: 无原生 AST 操作 API**
- `@tarojs/service` 的 `IPluginContext` 类型定义列出完整插件 API，但无 AST 相关接口
- 唯一注入路径：通过 `modifyWebpackChain` 注入自定义 babel loader
- **影响**: 代码生成器不能直接操作 Taro 的编译 AST，需要自行集成 babel 插件

**陷阱 2: 16 级非递归模板**
- `UnRecursiveTemplate` 类设置 `baseLevel=16`，生成 `tmpl_0` 到 `tmpl_15`
- `buildContainerTemplate` 在最深层生成 `comp` 重启循环
- **影响**: 模板生成逻辑复杂，不能简单地递归生成 WXML

**陷阱 3: 字符串级后处理**
- `modifyTemplateResult` 接收字符串，执行 `split/splice/join` 进行键盘附件注入
- WXML 生成存在非 AST 的字符串操作
- **影响**: 不能假设模板输出是纯净的 AST 结构

**核心结论**: 低代码平台的代码生成器**必须产出 Taro JSX/TSX 源码**（而非纯小程序原生代码），然后交给 Taro 的标准编译管线处理。这是由 Taro 的编译流程决定的：React/JSX 源码 → Babel + Webpack → 小程序原生代码。

### 10.4 实时预览的增量同步模式

**iofod WebSocket 增量同步架构** (GitHub 92 星, 参考价值有限)

- 模式：WebSocket 监听 Schema 变更 → 增量同步到预览端 → 局部更新渲染
- **优势**: 比全量轮询更高效，适合大页面的实时预览
- **劣势**: 社区采用度极低，Taro 支持被否决 (vote 0-2)
- **推荐**: 作为架构模式参考，不作为技术选型基础。实际实现可采用 Zustand + WebSocket 的增量同步

### 10.5 未覆盖的研究领域

以下领域在本次研究中未能深入，建议后续专项研究：

1. **医疗合规与安全**: 等保 2.0 三级要求对低代码平台的具体技术约束、低代码生成页面的安全审计流程、Schema 中 API 数据源的脱敏处理
2. **Taro 4.x Vite 编译模式**: 是否提供更好的 AST 操作能力或插件扩展点
3. **竞品商业产品**: 即速应用、微动天下、知晓云等的具体定价和技术架构
4. **NutUI + Formily 适配工作量**: 是否可通过 `createSchemaField` 标准方式实现，还是需要为每个组件编写专门的 adapter
