## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**预约功能流程：**
- **patient-miniapp 端**：选择科室 → 选择医生 → 选择日期时段 → 填写预约信息（就诊人+病情描述）→ 重复预约检查 → 提交 → 预约结果
- **admin 端**：预约列表（多维度筛选）→ 预约详情（时间线）→ 排队管理（叫号/过号/完成）
- **Server 端**：18 个预约相关 API 端点，覆盖完整 CRUD 和状态流转

**预约状态定义：**
| 状态码 | 名称 | 说明 |
|--------|------|------|
| 0 | 待支付 | PENDING |
| 1 | 已预约 | CONFIRMED |
| 2 | 已签到 | SIGNED |
| 3 | 候诊中 | WAITING |
| 4 | 就诊中 | SEEING |
| 5 | 已完成 | COMPLETED |
| 6 | 已取消 | CANCELLED |
| 7 | 已过期 | EXPIRED |
| 8 | 已关闭 | CLOSED |

**状态流转触发条件：**
- 创建预约 → 状态 1（已预约）
- 取消预约 → 状态 6（已取消），仅状态 0/1 可取消
- 签到 → 状态 2（已签到），仅状态 1 可签到
- 叫号 → 状态 3/4（候诊中/就诊中）
- 完成就诊 → 状态 5（已完成）
- 过号 → 状态 7（已过期）
- 取消签到 → 状态 1（已预约），仅超管可操作

|------|-----------------|-------|--------|

| 预约列表 | ✅ 已实现 | ✅ 已实现 | ✅ 已实现 |

**数据结构：**
- 预约表包含 30+ 字段，包括快照字段（就诊人/医生/规则时间窗）
- 前后端使用共享类型定义（packages/shared）
- 后端使用 Pydantic 自动转换 snake_case ↔ camelCase

### Designer — 用户视角

**页面清单：**
- **patient-miniapp**：预约列表页、医生详情页（选择时段）、预约挂号页、预约结果页、预约详情页、扫码签到页
- **admin**：预约列表页（ProTable）、预约详情页、签到队列页、排班日历（可创建预约）

**交互模式：**
- 表单验证：前端提交时校验必填项（scheduleId、patientId）
- 提交按钮：loading 状态控制、disabled 状态控制
- 反馈方式：Toast 提示（成功/失败）、页面跳转（预约成功）
- 取消确认：二次确认对话框

**时间选择机制：**
- 两步选择：日期横向滑动 → 上午/下午时段卡片
- 班次选择：底部 Sheet 弹出，显示具体时间、剩余号源、紧急程度
- 状态控制：未开放/已截止/约满/即将截止，不同状态有不同交互

**签到时间窗：**
- 返回三种状态：early（未到时间）/ available（可签到）/ late（已超时）
- 前端根据状态显示不同提示

### Engineer — 技术视角

**Server 端 API 设计：**
- 基础路由：`/api/v1/appointments`
- 认证方式：JWT Bearer Token
- 权限级别：普通用户/医生/管理员/超级管理员
- 参数验证：Pydantic Schema

**数据库设计：**
- appointments 表：主表，含快照字段
- appointment_checkins 表：签到审计日志
- schedules 表：排班表，含号源统计
- 规则引擎相关表：rule_sets、rule_windows、rule_booking_policies 等

**并发控制：**
- 分布式锁：按 schedule_id 级别加锁
- 锁超时：10 秒
- 重试次数：5 次
- 锁内操作：容量检查 → 重复预约检查 → 号源检查 → 创建预约 → 更新号源

**业务逻辑关键点：**
1. 预约创建：排班验证 → 规则引擎时间窗检查 → 规则验证 → 分布式锁 → 创建预约
2. 取消预约：权限验证 → 状态检查 → 时间窗检查 → 更新状态 → 恢复号源 → 候补递补
3. 签到：权限验证 → 状态检查 → 时间窗检查 → 签到次数限制 → 更新状态 → 审计日志

**前后端数据一致性：**
- 字段名转换：Pydantic alias_generator 自动转换
- 状态常量：前后端使用相同的数值定义
- 类型匹配：string/number/Date/DateTime 类型对应

## Round 2：辩论层

### 交叉评论投票矩阵

#### 简化投票矩阵（集中调度模式）

| 议题 | 裁决者立场 | Critic 质询 | 最终裁决 |
|------|-----------|------------|---------|
| 取消预约并发安全 | 需要修复 | 🚨 分布式锁缺失 | **确认问题存在** |
| 候补递补原子性 | 需要修复 | 🚨 状态不一致风险 | **确认问题存在** |
| 测试覆盖率 | 需要补充 | 🚨 零测试覆盖 | **确认问题存在** |
| 时区处理 | 需要统一 | 混用 utcnow 和本地时区 | **确认问题存在** |
| 前后端状态判断 | 需要验证 | 异常降级可能导致不一致 | **确认问题存在** |

### 独到发现

1. **取消预约缺少分布式锁保护**：恢复号源操作 `booked_slots - 1` 没有并发保护，在高并发取消场景下可能导致号源计数错误
2. **测试完全缺失**：apps/server 目录下没有任何测试文件，功能正确性完全依赖人工验证
3. **候补递补状态回滚风险**：如果递补后的预约创建失败，候补记录状态可能无法正确回滚

### Critic 质询

#### [Critic → Engineer] 质询 1：分布式锁的范围完整性存疑
**论据：** 取消预约流程中恢复号源没有使用分布式锁保护，`schedule.booked_slots = max(0, schedule.booked_slots - 1)` 可能产生竞态条件
**级别：** 🚨 关键

#### [Critic → Engineer] 质询 2：候补自动递补的原子性缺失
**论据：** 候补容量计算在锁外执行，如果递补后预约创建失败，状态回滚逻辑可能导致不一致
**级别：** 🚨 关键

#### [Critic → Engineer/PM] 质询 3：测试覆盖率为零
**论据：** 搜索 `test_*.py` 返回 No files found，复杂预约系统没有任何自动化测试
**级别：** 🚨 关键

#### [Critic → Engineer] 质询 4：时区处理的不一致性
**论据：** 候补服务使用 `datetime.utcnow()` 而签到使用 `Asia/Shanghai` 时区
**级别：** 普通

#### [Critic → Engineer] 质询 5：前端状态判断与后端异常降级不一致
**论据：** 规则引擎异常时降级到门店配置，前端可能显示错误状态
**级别：** 普通

### 🚨 Critic 关键质询追踪

| # | 关键质询内容 | 回应摘要 | 回应是否充分 | 处置 |
|---|------------|---------|------------|------|
