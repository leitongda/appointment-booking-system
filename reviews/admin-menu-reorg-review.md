# appointment-booking-system — 自适应多智能体研究画布

> 协作模式：对等协作
> 日期：2026-04-02
> 审查目标：Admin 端菜单结构重新分类整理 — 提出多种不同角度的菜单方案

---

## 模式选择

**选定模式：** 对等协作

**选择理由：** 用户明确要求"多种不同角度的菜单方案"，需要最大化视角碰撞。菜单分类是典型的跨职能权衡问题 — PM 关注业务语义，Designer 关注用户心智模型和工作流，Engineer 关注路由结构和权限边界。

## Round 1：事实层（只写事实，不评价）

### PM — 产品视角

**当前菜单分组（7 个一级分组）：**
1. 仪表盘 — 1 项
2. 平台管理 — 3 项（租户管理、订阅计划、小程序平台）
3. 组织与权限 — 8 项（门店、科室、角色权限、后台用户、操作日志、签到审计、在线用户、行为分析）
4. 医疗业务 — 7 项（医生、排班、预约、用户、就诊卡、病历、停诊审核）
5. 经营配置 — 11 项（预约规则、爽约黑名单、微信配置、基础设置、班次类型、规则组、诊费类型、诊费模板、预约须知、邮件模板、邮件接收人）
6. 内容与触达 — 3 项（内容管理、消息管理、用户反馈）

**角色-菜单可见性矩阵：**
| 角色 | 可见范围 |
|------|---------|
| SUPER_ADMIN | 全部 6 个分组 |
| PLATFORM_ADMIN | 平台管理 + 部分组织与权限 |
| TENANT_ADMIN | 仪表盘 + 组织与权限 + 医疗业务 + 经营配置 + 内容与触达 |
| STORE_ADMIN | 仪表盘 + 门店管理 + 医疗业务 + 部分经营配置 + 部分内容 |
| STORE_USER | 仪表盘 + 医生列表 + 排班列表 + 预约列表 + 患者列表 |

**核心业务流程依赖链：** 医生 → 排班 → 预约 → 签到 → 就诊 → 病历

**高频操作：** 医生管理、排班管理（9 个子功能）、预约管理（3 个子功能）
**低频配置：** 系统设置、邮件模板、规则组管理、班次类型

**分类维度：** 混合维度 — 业务域 + 用户角色 + 操作频率 + 系统层级

**分类不一致项：**
- "组织与权限"混合了业务实体（门店、科室）+ 权限管理（角色、用户）+ 运维监控（日志、审计、在线用户、行为分析）
- "经营配置"混合了业务规则 + 系统配置 + 通知配置
- 缺少独立的"数据分析"分组，统计功能分散在各模块

**行业参考差异：**
- 行业常见：组织管理与权限管理分开
- 行业常见：独立的统计报表分组
- 当前特色：SaaS 多租户的"平台管理"分组是行业差异化点

### Designer — 用户视角

**层级统计：**
- 6 个一级分组、最大深度 5 级
- 143 条总路由，55 条隐藏，62 条可见
- 子菜单最多：经营配置（11 项）、组织与权限（8 项）

**命名分析：**
- 17 个"名词+管理"（租户管理、门店管理...）
- 32 个"动词+名词"（新增租户、编辑门店...）
- 语义混淆："用户管理"（后台管理员）vs "用户列表"（C 端用户）

**图标：** 18 个图标中仅 1 个重复（apartment 用于"组织与权限"和"科室管理"）

**高频工作流路径：**
- 前台客服：签到队列 → 预约列表 → 用户列表（2 级路径）
- 科室主任：医生管理 → 排班管理（9 子功能）→ 预约管理 → 停诊审核（跨 3 个二级分组）
- 门店管理员：组织管理 + 后台用户 + 经营配置（3-4 级深度）

**隐藏路由：** 47% 路由隐藏，8 条动态菜单规则

**Layout 配置：** mix 模式（顶部+侧边），siderMenuType: group

### Engineer — 技术视角

**路由统计：**
- 143 条路由，55 条隐藏
- 最大 5 层路径（如 `/platform/miniapp-platform/company/:id/edit`）
- 路径命名：统一 kebab-case，编辑 `/create`、`/:id/edit`、`/:id`

**权限粒度：** 模块级 → 功能级 → 操作级，32 个 can* 函数

**页面组件：**
- 排班模块最多（26 个组件）
- `./system/settings` 被 4 个路由共享（预约规则、黑名单、微信配置、基础设置）
- 表单复用模式：新增/编辑共用 form.tsx

**前后端映射不一致：**
- 排班管理：前端 1 个菜单 → 后端 7 个 API 模块
- 经营配置：前端 1 个菜单 → 后端 7 个 API 模块
- 仪表盘：前端有菜单 → 后端无对应模块

**技术约束：**
- Umi 4 路由配置规范
- ProLayout 菜单渲染 + 受控展开
- 动态菜单通过正则匹配 + children 追加实现
- 权限通过 access 字段关联 hasPermission 函数

### 各方提出的菜单方案汇总

#### 方案 A：业务流程驱动（PM 提出）
- 一级分组：工作台、预约运营、患者管理、医疗资源、门店与组织、内容与消息、系统设置、平台管理、运维监控（9 个）
- 核心：将排班配置（班次、规则组）从经营配置移入预约运营，形成闭环
- 改动量：中等

#### 方案 B：用户角色驱动（PM 提出）
- 一级分组按角色视角划分：门店管理、科室运营、前台服务、运营管理、系统管理、平台管理（7 个）
- 核心：每个人只看到自己相关的菜单
- 改动量：大（需按角色动态渲染整个分组）；且基础假设需修正（权限码驱动非角色驱动）

#### 方案 C：任务流驱动（Designer 提出）
- 一级分组：医疗业务、患者管理、组织架构、内容运营、系统管理、平台管理、运维监控（7 个）
- 核心：签到队列提升为独立菜单，系统管理按域分子分组（排班配置/预约配置/诊费配置/通知配置/门店配置）
- 改动量：中等

#### 方案 D：扁平化（Designer 提出）
- 一级分组：业务管理、组织管理、运营中心、系统设置（4 个）
- 核心：利用 siderMenuType: group 在侧边栏做视觉分组，大幅减少顶部导航项
- 改动量：较大（设置页合并需重构组件）

#### 方案 E：技术模块对齐（Engineer 提出）
- 一级分组：仪表盘、平台管理、机构管理、医疗服务、内容与触达、系统管理、运维监控（7 个）
- 核心：前端路径与后端 API 模块 1:1 对齐，消除 organization/system 语义错位
- 改动量：约 100 行，2 个文件，2-4h

## Round 3：共识层

### ✅ 共识项

1. **"经营配置"需要拆分**
   - **结论：** 经营配置 11 项是垃圾桶式分组，包含排班基础数据（班次类型）、仅超管可见配置（规则组）、医疗定价（诊费）、系统配置（微信/基础设置）、通知配置（邮件）。按业务归属分散到对应分组。
   - **处置建议：** 班次类型 → 排班管理附近；诊费 → 医疗资源或独立诊费分组；邮件/微信 → 系统设置；规则组 → 系统管理
   - **优先级：** P0
   - **成本：** 2h

2. **"组织与权限"需要拆分运维监控**
   - **结论：** 操作日志、签到审计、在线用户、行为分析不属于"组织与权限"，它们是运维功能。独立为"运维监控"分组（仅超管可见）。
   - **优先级：** P0
   - **成本：** 1h

3. **命名混淆需要修正**
   - **结论：** "用户管理"（后台管理员）vs "用户列表"（C 端患者）需修正。建议：后台用户 → "后台用户"（已部分修正），C 端用户 → "患者管理"。
   - **优先级：** P0
   - **成本：** 0.5h

4. **排班配置就近原则**
   - **结论：** 班次类型、规则组管理是排班的前置依赖，当前在经营配置中，与排班操作流程割裂。移至排班管理附近（可以是排班管理的子分组或系统管理中的"排班配置"子分类）。
   - **优先级：** P1
   - **成本：** 1h

5. **Settings 组件拆分**
   - **结论：** Critic 指出 settings.tsx 是 1015 行上帝组件，包含 7 个不相关业务域的 Tab。应拆分为独立页面组件。拆分后菜单自然跟随组件边界重新组织。
   - **优先级：** P1
   - **成本：** 4h

6. **重组工程成本远低于预期**
   - **结论：** Umi 4 配置式路由与页面文件解耦，重组主要是 routes.ts + access.ts 的文本修改，页面组件无需物理迁移。约 100 行代码，2-4h 可完成路由调整。
   - **优先级：** 信息项
   - **成本：** —

7. **角色-分组对应关系不应被破坏**
   - **结论：** Critic 质询 3 有效——当前混合维度虽然不完美，但保持了"门店管理员看组织与医疗"、"超管看全部分组"的角色-分组对应。重组时应保持或强化这种对应，而非模糊化。

### ⚡ 分歧项

1. **重组力度：增量微调 vs 全面重组**
   - **PM 立场：** 倾向方案 A（业务流程驱动），拆分为 9 个一级分组
   - **Designer 立场：** 方案 C（7 个分组）可短期落地，方案 D（4 个分组）适合大版本
   - **Engineer 立场：** 方案 E（7 个分组），与后端模块对齐
   - **Critic 立场：** 质疑是否只需命名修正（质询 7），不改变分组
   - **裁决：** 采用**增量重组策略**——先执行共识项 1-3（P0），再根据效果决定是否进一步调整

2. **"医疗业务"是否需要拆分**
   - **PM 立场：** 拆分为"预约运营"+"患者管理"+"医疗资源"（方案 A）
   - **Designer 立场：** 保留但精简，把配置类移出（方案 C）
   - **Engineer 立场：** 保留，但路径从 `/medical-services` 缩短为 `/medical`（方案 E）
   - **裁决：** 暂不拆分"医疗业务"，但将低频配置项（停诊审核可保留，就诊卡考虑合并到患者管理）移出

### 被低估的优势

1. **当前分组对 SaaS 多租户场景的适配** — "平台管理"分组天然隔离了平台级功能，这是很多单租户系统不具备的设计
2. **Umi 4 配置式路由的灵活性** — 重组几乎不需要动页面组件，工程成本远低于直觉预期
3. **权限码驱动模型的可扩展性** — 虽然不是"角色驱动"，但功能权限码模型比角色模型更灵活，适合细粒度控制

## 摘要

**使用模式：** 对等协作

**关键共识：**
- 7 项达成共识（3 项 P0 + 2 项 P1 + 2 项 P2）

**关键分歧：**
- 2 项需要权衡（重组力度：增量 vs 全面；医疗业务是否拆分）

**提出的菜单方案：**
- 方案 A：业务流程驱动（PM，9 分组）
- 方案 B：用户角色驱动（PM，7 分组）— 基础假设需修正
- 方案 C：任务流驱动（Designer，7 分组）
- 方案 D：扁平化（Designer，4 分组）
- 方案 E：技术模块对齐（Engineer，7 分组）
- **推荐方案：** 渐进式重组（Engineer 骨架 + PM 分类 + Designer 任务流，7 分组）

**Critic 关键洞察：**
- settings.tsx 是 1015 行上帝组件，菜单重组应配合组件拆分
- 权限模型是功能码驱动而非角色驱动，PM 方案 B 的基础假设需修正
- "混合维度"不一定是问题，但"垃圾桶式分组"（经营配置）是问题

**Top 3 P0 行动：**
1. 拆分"经营配置"（2h）
2. 独立"运维监控"分组（1h）
3. 修正命名混淆（0.5h）
