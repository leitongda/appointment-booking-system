### Engineer — 技术视角

**存储层事实：**
- 7张排班相关数据表：schedules, schedule_templates, schedule_suspensions, schedule_generation_logs, rest_days, shift_types, rule_set_shift_types
- 索引：所有 tenant_id 有索引；rule_sets 有复合索引 (enabled, priority)

**核心引擎事实：**
- 排班生成算法：模板驱动，遍历日期范围 → 检查星期匹配 → 检查排班模式 → 检查休息日 → 时间分割 → 去重检查 → 创建记录

- 排班冲突检测：在分布式锁内执行，支持自定义排班覆盖普通排班

- 排班状态：0=停诊, 1=正常
- 错误处理：单模板失败不影响其他，记录错误后继续处理
- 去重机制：仅依赖应用层代码检查，无数据库唯一约束兜底

**API/协议事实：**
- 排班模块14个API端点，班次类型6个端点

### 独到发现

1. **排班生成管道（pipeline）缺少校验层** — 跨产品+工程视角：排班生成从模板到记录是一条单向管道（模板→日期遍历→时间分割→创建），中间没有"规则引擎校验"这个阶段。规则引擎只在预约消费侧（service_booking.py）被调用。这意味着系统在"生产侧"可以制造出"消费侧"无法使用的产品。这不是单一模块的 bug，而是数据流设计层面的缺失。

2. **分布式锁的"检查-加锁"间隙** — 跨工程+安全视角：当前去重流程是"检查不存在 → 加锁 → 再检查 → 创建"。两个 worker 可以同时通过第一次"检查不存在"，然后各自加锁创建。虽然锁内还有第二次检查（_create_schedule_if_not_exists），但更好的方式是在数据库层面用唯一约束兜底，将应用层防重作为第一道防线，数据库约束作为第二道。

3. **排班权重系统是差异化优势但前端呈现不足** — 跨产品+设计视角：权重系统（停诊>自定义>休息日>普通）是本项目的差异化功能，但前端只在 rest-day.tsx 的一行注释中提到权重规则。用户无法直观理解为什么某条排班"被覆盖"或"未生效"。在排班列表和日历中缺少权重影响的可视化说明。

## Round 3：共识层

### ✅ 共识项

1. **排班生成需集成规则引擎校验（幽灵排班问题）**
   **结论：** 排班生成管道（service_generation.py）需在创建排班记录前校验规则引擎约束（时间窗、容量策略），防止生成不可预约的"幽灵排班"。
   **建议行动：** 在 `_generate_from_template_internal` 方法中增加规则引擎校验调用；排班预览 API 同步展示校验结果；前端预览界面标记不可预约的排班。
   **成本估算：** 后端 ~8h（Engineer），前端 ~4h（Designer），合计 ~12h
   **优先级：** P0

2. **添加数据库唯一约束保障去重安全**
   **结论：** Schedule 表缺少 (doctor_id, schedule_date, time_slot) 唯一约束。当前去重完全依赖应用层代码，并发场景下有竞态风险。
   **建议行动：** 添加 Alembic 迁移创建唯一约束；service_mutation.py 中捕获 IntegrityError 作为兜底去重。
   **成本估算：** ~4h（Engineer）
   **优先级：** P0

3. **排班权重系统前端可视化增强**
   **结论：** 排班权重（停诊>自定义>休息日>普通）是差异化优势，但用户无法直观理解排班覆盖关系。排班列表中日历视图中缺少权重影响的可视化说明。
   **建议行动：** 排班列表增加"生效状态"字段和覆盖原因提示；日历视图中被覆盖的排班增加视觉区分（灰色+Tooltip 说明原因）。
   **成本估算：** ~8h（Designer）
   **优先级：** P1

4. **排班规则表单交互优化**
   **结论：** 首次配置排班（创建模板→生成）约 8 步，无操作引导。规则表单单步 12 字段 7 必填，对新手有认知负担。
   **建议行动：** 为排班规则表单添加可选的步骤引导（Step 1: 基本信息 → Step 2: 时间配置 → Step 3: 高级设置）；首次使用时显示简短引导提示。
   **成本估算：** ~12h（Designer）
   **优先级：** P1

5. **排班预览增强：展示规则引擎校验结果**
   **结论：** 排班预览目前只展示时间和号源信息，未展示规则引擎是否允许该排班被预约。
   **建议行动：** 预览 API 返回每条排班的规则校验状态；前端用颜色/图标标记"可预约"/"规则限制"/"不可预约"。
   **成本估算：** 后端 ~4h（Engineer），前端 ~4h（Designer），合计 ~8h
   **优先级：** P1

6. **无障碍访问改进**
   **结论：** 排班页面无 aria 属性，日历组件等自定义组件缺少键盘导航支持。
   **建议行动：** 为日历单元格、排班状态指示器添加 aria-label；为关键操作按钮添加 aria-describedby 提示。
   **成本估算：** ~4h（Designer）
   **优先级：** P1

7. **排班统计增强**
   **结论：** 当前统计（月度/时段/预约率/CSV）为基础功能。缺少利用率趋势、峰值分析、医生工作量对比。
   **建议行动：** 添加趋势图表（周/月排班利用率变化）；添加医生工作量对比视图；添加高峰时段热力图。
   **成本估算：** ~16h（Engineer + Designer）
   **优先级：** P2

8. **排班审批流程**
   **结论：** 当前无审批流程。医生只能申请停诊，无法申请调班。开放医生自主调班的前提是先有审批机制。
   **建议行动：** 设计排班变更审批流程（医生申请→管理员审批→生效）；实现审批状态机；医生端增加调班申请入口。
   **成本估算：** ~40h（PM + Designer + Engineer）
   **优先级：** P2

9. **跨院区排班复制**
   **结论：** 当前复制功能仅限同门店。多院区组织需要跨门店复制排班规则。
   **建议行动：** 扩展 copy_to_doctors 支持跨门店医生选择；增加门店级参数覆盖。
   **成本估算：** ~12h（Engineer）
   **优先级：** P2

### ⚡ 分歧项

1. **移动端排班日历适配**
   **各方立场：**
   - Designer：标记为响应式设计缺失
   - Critic：后台管理系统，桌面端为主，正确取舍
   **裁决：** 当前为正确取舍。若未来有移动端管理需求再重新评估。
   **决策依据：** 排班日历信息密度高，移动端体验难以保证；Ant Design Pro 后台以桌面为主流场景。

2. **医生自主调班权限**
   **各方立场：**
   - PM：竞品普遍支持，标记为缺失
   - Critic：缺少审批流程时，限制权限是更安全的选择
   **裁决：** 正确取舍。优先级顺序：审批流程（P2）→ 医生调班权限（P2 后期或更晚）。
   **决策依据：** 无审批的自主调班风险高于收益。

3. **AI 排班推荐**
   **各方立场：**
   - PM：部分竞品有此功能
   - Critic：行业实验阶段，不宜作为标准功能对比
   **裁决：** 不列为当前缺失。数据基础成熟后再考虑。
   **决策依据：** AI 排班需要大量历史数据支撑，当前系统数据积累不足以支撑有效推荐。

## 被低估的优势

1. **排班权重系统**（停诊>自定义>休息日>普通）是本项目的差异化功能。多数竞品采用简单的覆盖逻辑，本项目的多层级权重系统可以处理更复杂的排班场景。建议在前端更好地可视化和解释权重逻辑。

2. **分布式锁细粒度设计**（tenant+doctor+date+time_slot）是正确的高并发策略。在多租户 SaaS 环境下，细粒度锁避免了不同租户、不同医生的排班操作互相阻塞。

3. **规则引擎多层级匹配**（doctor > department > store > tenant）是灵活的架构选择。允许不同粒度的规则配置，从全局默认到医生个性化。

4. **Service 分层架构**（QueryMixin + MutationMixin + GenerationMixin）职责清晰，便于独立测试和扩展。

5. **颜色+文字双重编码**的排班状态显示是无障碍方面的好的实践。

## 摘要

**使用模式：** 集中调度

**关键共识：**
- 8 项达成共识（2 项 P0 + 4 项 P1 + 3 项 P2）

**关键分歧：**
- 3 项裁决完毕（移动端适配、医生调班、AI推荐——均为正确取舍）

**Top 3 P0 行动：**
1. 排班生成集成规则引擎校验 — 12h — 解决"幽灵排班"数据正确性问题
2. 添加数据库唯一约束 (doctor_id, schedule_date, time_slot) — 4h — 兜底并发去重安全
3. 排班预览展示规则校验结果 — 8h (P1，与 P0 配套)

**Critic 关键洞察：**
- PM 对规则引擎集成状态的定性有误——真正问题不在绑定关系，而在排班生成管道缺少校验层
- 三方均遗漏了排班生成与规则引擎的脱节——这是本次评审最有价值的发现
- 多个被标记为"缺失"的功能（移动端适配、医生调班）在当前上下文中是正确的产品取舍
